# 為什麼狀態檔對 AI 代理程式失效

狀態檔的設計建立在 AI 代理程式會違反的假設之上：一次只有一個寫入者、變更會批次彙整成不常執行且經人工審查的 apply，以及能容忍狀態在兩次重新整理之間過時的工作流程。代理程式會並行、持續地行動，並根據所獲得的任何事實進行推理；如果這些事實來自狀態檔，代理程式就是根據一份過時且不完整的現實副本在推理。

## 明確列出這些假設 {#the-assumptions-made-explicit}

狀態檔模型在下列情況下可行：

1. **寫入是序列化的**。狀態鎖定假設爭用很少發生。人類團隊一天只 apply 幾次；鎖定爭用屬於邊緣案例。
2. **讀取發生在 plan 階段**。狀態會在人員執行 plan 時重新整理；中間的過時狀態不會被察覺，因為沒有人在看。
3. **受管理的集合就是相關的集合**。狀態檔只描述該工具所建立的資源。工作流程假設集合之外沒有任何重要的東西存在。
4. **錯誤由專家修復**。損毀或分歧的狀態，由從業人員以狀態修補（匯入、移動、手動編輯）來修正。

在代理式運作下，每項假設都會失效。代理程式以秒為單位行動，因此序列化寫入會成為輸送量上限，鎖定爭用則成為常態。代理程式持續觀察，因此兩次重新整理之間的過時狀態會變成一連串錯誤的前提。代理程式經常被問到整個環境的狀況（「是否有任何東西公開暴露？」），而受管理集合之外的答案正是關鍵所在。此外，損毀狀態的代理程式無法可靠地自行進行狀態修補，因為修復流程原本就假設有人類判斷。

## 更深層的問題：副本就是介面 {#the-deeper-problem-the-copy-is-the-interface}

這一切都可歸結為一個設計決策：狀態檔將基礎架構狀態的*副本*當作系統的工作介面。每份副本都有同步問題，而副本的每個取用者都會繼承這個問題。[基礎架構漂移](/ai/canonical-definitions/what-is-infrastructure-drift)不是營運上的意外，而是副本在實際狀態會透過其他途徑（主控台、自動調整器、其他工具、其他代理程式）改變的環境中的穩態行為。

人工工作流程以流程來吸收這個問題：變更凍結、單一工具強制規定、定期調和。代理式環境則做不到，因為代理程式的價值就在於頻繁且獨立地行動，而這正是使協調一致的副本無法維護的流量模式。

## 取而代之的基本機制 {#the-replacement-primitive}

控制平面本身就已經是一致、具權威性且並行安全的狀態存放區，由雲端供應商負責運作。代理程式需要的是一個符合其工作方式的控制平面介面：對目前狀態進行宣告式查詢、跨供應商保持一致，且變更以相同的文法表達並由政策管控。這就是 StackQL 實作的模型：

```sql
SELECT instance_id, instance_type, launch_time
FROM aws.ec2.instances
WHERE region = 'us-east-1';
```

結果在執行當下為真，包含未受管理的資源，不需要鎖定，也不需要修復工作流程，因為沒有任何東西會損毀。識別碼對應和相依性排序（狀態檔的正當職責）會移至查詢引擎和部署協調（stackql-deploy）中，而不是放在代理程式必須保持一致的可變動產物中。
