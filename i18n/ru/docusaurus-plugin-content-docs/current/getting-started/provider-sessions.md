Сеанс может привязать провайдера к псевдониму с собственными учетными данными, меткой tenancy, значениями параметров по умолчанию и ограничениями параллельности запросов, поэтому к нескольким учетным записям или тенантам одного провайдера можно выполнять запросы в одном сеансе и даже в одной инструкции.  Поля учетных данных также можно переопределить для сеанса, а секреты - хранить в памяти сеанса или, если оператор явно включит такую возможность, в хранилище секретов операционной системы.  Эти возможности настраиваются с помощью [`SET`](/language-spec/set) и [`UNSET`](/language-spec/unset) и доступны в StackQL `v1.0` и более поздних версиях.

Область действия всех описанных здесь настроек - текущий сеанс.  Независимые подключения к серверу `stackql srv` не используют общие привязки или секреты, а каждый MCP-запрос - это отдельный сеанс, поэтому при работе с MCP-сервером выполняйте настройку и запросы в одном пакете инструкций.

## Псевдонимы провайдеров {#provider-aliases}

Инструкция `SET "$.providers.<alias>"` привязывает псевдоним к провайдеру.  Значение - это JSON-документ, хранящийся в строке:

| Ключ | Обязательный | Описание |
|--|--|--|
| `provider` | Да | Канонический провайдер, которому соответствует псевдоним, например `aws`. |
| `tenancy` | Да | Метка группировки, например имя учетной записи или тенанта.  StackQL не сверяет ее с провайдером. |
| `auth` | Один из ключей `auth` или `auth_secret` | Документ аутентификации в формате псевдонима, который отличается от записи провайдера в объекте [`--auth`](/command-line-usage/global-flags): для AWS используются ключи `access_key_id_env_var` и `secret_access_key_env_var`, а не `keyIDenvvar` и `credentialsenvvar`, а ключ, неизвестный формату псевдонима, приводит к ошибке `invalid session configuration field or type`.  Псевдоним не заимствует учетные данные канонического провайдера. |
| `auth_secret` | Один из ключей `auth` или `auth_secret` | Имя [секрета сеанса](#session-secrets), в котором хранится документ аутентификации. |
| `params` | Нет | Значения по умолчанию для объявленных параметров провайдера, включая объявленные параметры сервера.  Предикат в запросе переопределяет значение по умолчанию. |
| `tuning` | Нет | Ограничения `max_concurrent` и `max_per_host` для запросов псевдонима.  Псевдонимы с общими провайдером и tenancy используют эти ограничения совместно и должны объявлять одинаковые настройки. |
<br/>
В следующем примере две учетные записи AWS привязываются к отдельным псевдонимам, каждый из которых читает ключи из переменных среды со своими именами, и к обеим учетным записям выполняется запрос в одной инструкции:

```sql
SET "$.providers.production" = '{
  "provider": "aws",
  "tenancy": "production-account",
  "auth": {
    "type": "aws_signing_v4",
    "access_key_id_env_var": "PRODUCTION_AWS_ACCESS_KEY_ID",
    "secret_access_key_env_var": "PRODUCTION_AWS_SECRET_ACCESS_KEY"
  },
  "params": {"region": "ap-southeast-2"},
  "tuning": {"max_concurrent": 4, "max_per_host": 4}
}';

SET "$.providers.development" = '{
  "provider": "aws",
  "tenancy": "development-account",
  "auth": {
    "type": "aws_signing_v4",
    "access_key_id_env_var": "DEVELOPMENT_AWS_ACCESS_KEY_ID",
    "secret_access_key_env_var": "DEVELOPMENT_AWS_SECRET_ACCESS_KEY"
  },
  "params": {"region": "ap-southeast-2"},
  "tuning": {"max_concurrent": 2}
}';

SELECT name, 'production' AS account FROM production.s3.buckets
UNION ALL
SELECT name, 'development' AS account FROM development.s3.buckets;
```

Ссылки на переменные среды определяются из среды процесса StackQL; локальной среды сеанса нет.  Для временных учетных данных AWS также нужно поле с токеном сеанса или ссылка на соответствующую переменную среды.

В инструкциях метаданных и данных псевдоним ведет себя как его провайдер: `SHOW`, `DESCRIBE`, `SELECT`, `INSERT`, `UPDATE`, `DELETE` и `EXEC` принимают псевдоним вместо имени провайдера.  Псевдонимы не распространяются на нативные встроенные отношения и на отношения IaC в предварительной версии.  Ветви `UNION ALL`, использующие разные псевдонимы, выполняются последовательно.

Каждый запрос получает независимый снимок учетных данных псевдонима.  Изменение привязки влияет на последующие запросы, но не на уже выполняющийся.  Инструкция `UNSET "$.providers.<alias>"` удаляет привязку.

## Переопределение полей учетных данных {#overriding-credential-fields}

Инструкция `SET "$.auth.<provider>.<field>"` изменяет одно поле контекста аутентификации провайдера для сеанса; имена полей - это ключи записи провайдера в `--auth`:

```sql
SET "$.auth.github.password_var" = 'GITHUB_TOKEN_READONLY';
SELECT name FROM github.repos.repos WHERE org = 'stackql';
UNSET "$.auth.github.password_var";
```

Как и в случае псевдонимов, изменение применяется к запросам, запущенным после `SET`.  Запросы к провайдеру, аутентификация которого сброшена или у псевдонима которого нет пригодного `auth`, завершаются ошибкой еще до отправки какого-либо запроса к API.

## Секреты сеанса {#session-secrets}

По умолчанию у каждого сеанса есть хранилище секретов только в памяти, которое не требует настройки.  Инструкция `SET "$.secrets.<name>"` сохраняет строковый литерал, обычно JSON-документ аутентификации, а псевдоним провайдера ссылается на него через `auth_secret`:

```sql
SET "$.secrets.production" = '{"type":"aws_signing_v4","access_key_id_env_var":"PRODUCTION_AWS_ACCESS_KEY_ID","secret_access_key_env_var":"PRODUCTION_AWS_SECRET_ACCESS_KEY"}';
SET "$.providers.production" = '{"provider":"aws","tenancy":"production-account","auth_secret":"production","params":{"region":"ap-southeast-2"}}';

SELECT name FROM production.s3.buckets;

UNSET "$.secrets.production";
```

Смена секрета влияет на последующие запросы; после его удаления последующие обращения к нему завершаются ошибкой.  Новый сеанс получает новое пустое хранилище, а при завершении сеанса оно освобождается.  Инструкция `UNSET "$.secret_store"` отменяет текущую привязку хранилища и начинает заново с пустой памяти сеанса.

Обычное использование учетных данных и инструкции `SET`, сохраняющие переменные или конфигурацию, не записывают секреты в SQL-бэкенд.  За размещение конфиденциальных данных в обычной переменной или таблице отвечает вызывающая сторона.

## Постоянные хранилища секретов ОС {#persistent-os-secret-stores}

Постоянное хранение по умолчанию отключено, и включить его может только оператор, запустив StackQL с флагом `--allow-persistent-secrets`; из SQL его предоставить нельзя.  Если флаг задан, сеанс выбирает хранилище ОС так:

```sql
SET "$.secret_store" = '{"backend": "os", "namespace": "stackql/provider-auth"}';
```

Хранилищем служит macOS Keychain, Linux Secret Service (`secret-tool` с работающей службой сеанса) или Windows Credential Manager.  Принимается только бэкенд `os`: хранилища в простых файлах, пути к файлам и любой неявный резервный вариант с файлом отклоняются даже при заданном флаге, а недоступный механизм ОС приводит к ошибке, а не к переходу на файл.

Значения, записанные в хранилище ОС, сохраняются после завершения SQL-сеанса и удаляются явно инструкцией `UNSET "$.secrets.<name>"`.  Сброс привязки хранилища не удаляет уже сохраненные значения.  Доступ к хранилищу определяется удостоверением процесса StackQL в операционной системе; пространство имен не является механизмом контроля доступа для отдельных пользователей, поэтому не рассматривайте эту явно включаемую возможность как многопользовательское хранилище секретов.

## Значения секретов в SQL {#secret-values-in-sql}

Значения секретов никогда не подставляются в SQL путем разыменования, если оператор не запустил StackQL с флагом `--allow-secret-dereference`.  С этим флагом в выражениях ссылки, такие как `"$secrets.production"`, `"$secrets.production.credentials"`, `"$auth.github.password"` и `"$providers.production.auth.credentials"`, заменяются значениями:

```sql
SELECT upper("$secrets.production.credentials") AS credential;

/*
-- the same statement in a session started without --allow-secret-dereference
SELECT upper("$secrets.production.credentials") AS credential;
-- FAILS with secret variable dereferencing is disabled
*/
```

Если StackQL запущен без флага, та же инструкция отклоняется еще до вычисления чего-либо, как показывает закомментированная копия.  Флаг подтверждает, что явно разыменованные значения могут попасть в промежуточную среду SQL, результаты, журналы и сохраняемые артефакты запросов.  Для обычной аутентификации провайдера он не нужен.

## Разрешения {#permissions}

Если включено [управление доступом](/command-line-usage/access-management), для чтения переменных и секретов требуется разрешение `session/variables:read`, а для `SET` или `UNSET` - `session/config:write`.  Перед выполнением псевдоним авторизуется как соответствующий ему канонический провайдер.  Владение и предоставление разрешений на уровне отдельных переменных и секретов не реализованы.
