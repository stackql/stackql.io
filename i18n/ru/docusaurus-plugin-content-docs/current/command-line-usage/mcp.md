Команда для запуска StackQL в качестве сервера Model Context Protocol (MCP), которая позволяет ИИ-агентам и ИИ-ассистентам взаимодействовать с облачной инфраструктурой с помощью возможностей StackQL по выполнению запросов.

:::info[Что такое MCP?]

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/) - это открытый протокол, который стандартизирует взаимодействие ИИ-приложений с внешними источниками данных и инструментами.  Запустив StackQL в качестве MCP-сервера, вы позволите ИИ-агентам (Claude, Cursor, Continue, собственным агентам и т. д.) выполнять запросы к облачной инфраструктуре разных провайдеров и управлять ею на естественном языке.

:::

* * *

### Синтаксис {#syntax}

`stackql mcp [flags]` для автономного MCP-сервера.

`stackql srv [flags]` для запуска MCP-сервера вместе с сервером сетевого протокола PostgreSQL в одном процессе.

* * *

### Режимы развертывания {#deployment-modes}

MCP-сервер StackQL можно развернуть в трех разных конфигурациях в соответствии с различными архитектурными требованиями.  Примеры ниже явно включают работу без аутентификации с помощью `"allow_unauthenticated": true`, что подходит для локальной разработки; для сервера, к которому может обратиться другой процесс или хост, вместо этого настройте токен bearer (см. [Аутентификация HTTP-клиентов](#http-client-authentication)).

#### 1. Автономный MCP-сервер {#1-standalone-mcp-server}

Запустите StackQL как выделенный MCP-сервер на указанном порту.

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true}}'
```

**Сценарий использования:** когда вам нужен только доступ по протоколу MCP и не требуется совместимость с сетевым протоколом PostgreSQL.

#### 2. MCP + сервер PostgreSQL (в памяти) {#2-mcp--postgresql-server-in-memory}

Запустите серверы MCP и PostgreSQL одновременно со взаимодействием между ними в памяти.

```bash
stackql srv \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true}}' \
  --pgsrv.port 5665
```

**Сценарий использования:** когда вам нужен и доступ по протоколу MCP для ИИ-агентов, и сетевой протокол PostgreSQL для традиционных клиентов баз данных, с максимальной производительностью за счет взаимодействия в памяти.

#### 3. MCP + сервер PostgreSQL (обратный прокси) {#3-mcp--postgresql-server-reverse-proxy}

Запустите оба сервера со взаимодействием по TCP, которое поддерживает распределенные развертывания и шифрование TLS.

```bash
stackql srv \
  --mcp.server.type=reverse_proxy \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9004", "allow_unauthenticated": true}, "backend": {"dsn": "postgres://stackql:stackql@127.0.0.1:5446?default_query_exec_mode=simple_protocol"}}' \
  --pgsrv.port 5446
```

**С шифрованием TLS:**

```bash
stackql srv \
  --mcp.server.type=reverse_proxy \
  --mcp.config '{"server": {"tls_cert_file": "/path/to/server_cert.pem", "tls_key_file": "/path/to/server_key.pem", "transport": "http", "address": "127.0.0.1:9004", "auth_token_env_var": "STACKQL_MCP_TOKEN"}, "backend": {"dsn": "postgres://stackql:stackql@127.0.0.1:5446?default_query_exec_mode=simple_protocol"}}' \
  --pgsrv.port 5446
```

TLS шифрует транспорт, но не аутентифицирует клиента, поэтому в этом примере также требуется токен bearer, хранящийся в `STACKQL_MCP_TOKEN`.

**Сценарий использования:** когда нужно разделить рабочие нагрузки MCP и PostgreSQL между разными процессами или хостами либо когда требуется шифрование TLS для конечной точки MCP.

### Параметры конфигурации {#configuration-options}

#### Тип MCP-сервера {#mcp-server-type}

| Тип | Описание |
|--|--|
|`http`|Режим прямого HTTP-сервера - MCP-запросы обрабатываются движком StackQL внутри процесса.|
|`reverse_proxy`|Режим обратного прокси - MCP-запросы передаются базовому серверу PostgreSQL через настроенный DSN.  Используется с `stackql srv`.|
|`stdio`|Транспорт через стандартный ввод-вывод - сервер читает запросы из `stdin` и пишет ответы в `stdout`.  Используется MCP-клиентами, встроенными в редакторы (Claude Desktop, Cursor и т. д.).|

#### Формат журнала MCP {#mcp-log-format}

Флаг `--mcp.log.format` выбирает кодировку журнала аудита: `jsonl` (по умолчанию) или `otel` (записи журнала OpenTelemetry в формате OTLP/JSON).  Он переопределяет `server.audit.format` в объекте конфигурации.  См. [Формат журнала](#log-format).

#### Версия протокола MCP {#mcp-protocol-version}

Флаг `--mcp.protocol.version` задает самую новую ревизию протокола, которую объявляет сервер: `auto` (по умолчанию, все поддерживаемые ревизии), `2026-07-28` (только без сеанса) или более старую ревизию, например `2025-11-25` (эта ревизия и более ранние).  Он переопределяет `server.protocol_version` в объекте конфигурации.  См. [Закрепление ревизии](#pinning-the-revision).

#### Объект конфигурации MCP {#mcp-configuration-object}

Флаг `--mcp.config` принимает JSON-объект со следующей структурой.

##### Конфигурация сервера {#server-configuration}

| Поле | Описание | Обязательный |
|--|--|--|
|`server.transport`|Транспортный протокол - `http` или `stdio`.|Да|
|`server.address`|Адрес и порт, к которым привязывается MCP-сервер (например, `127.0.0.1:9912`).  Только для транспорта HTTP.|Для `http`|
|`server.tls_cert_file`|Путь к файлу сертификата TLS для HTTPS.|Нет|
|`server.tls_key_file`|Путь к файлу закрытого ключа TLS для HTTPS.|Нет|
|`server.auth_token_env_var`|Имя переменной среды, в которой хранится заранее согласованный токен bearer.  Если поле задано, каждый HTTP-запрос должен содержать `Authorization: Bearer <token>`; сервер не запускается, если переменная не задана или пуста.  См. [Аутентификация HTTP-клиентов](#http-client-authentication).|Это поле или `allow_unauthenticated`, для `http`|
|`server.allow_unauthenticated`|Явное включение работы транспорта HTTP без аутентификации клиентов.  По умолчанию: `false`.|Это поле или `auth_token_env_var`, для `http`|
|`server.mode`|Контракт безопасности, который контролирует операции изменения данных и операции жизненного цикла.  Одно из значений: `read_only`, `safe` (по умолчанию), `delete_safe`, `full_access`.  См. [Режимы сервера](#server-modes).|Нет|
|`server.read_only`|**Прежний** логический псевдоним для `mode: read_only`.  Если заданы оба поля, приоритет имеет `mode`.|Нет|
|`server.stateless`|Обслуживание Streamable HTTP без сеансов (без `Mcp-Session-Id`) - именно так ревизия протокола `2026-07-28` обслуживается по HTTP.  По умолчанию: `false`.  Игнорируется для `stdio`.  См. [Поддержка ревизий протокола](#protocol-revision-support).|Нет|
|`server.protocol_version`|Самая новая объявляемая ревизия протокола: `auto` (по умолчанию), `2026-07-28` или более старая ревизия, например `2025-11-25`.  `2026-07-28` подразумевает `stateless` для Streamable HTTP.  См. [Закрепление ревизии](#pinning-the-revision).|Нет|
|`server.audit`|Конфигурация подсистемы аудита, включая `audit.format` (`jsonl` или `otel`).  См. [Журнал аудита](#audit-log).|Нет|

##### Конфигурация бэкенда (только режим обратного прокси) {#backend-configuration-reverse-proxy-mode-only}

| Поле | Описание | Обязательный |
|--|--|--|
|`backend.dsn`|Строка подключения PostgreSQL к серверу StackQL, который работает как бэкенд.|Да (для `reverse_proxy`)|

<br />

:::info

Для наилучшей совместимости DSN бэкенда должен включать параметр `default_query_exec_mode=simple_protocol`.

:::

##### Списки разрешенных {#allowlists}

| Поле | Описание |
|--|--|
|`enabled_tools`|Массив имен инструментов, которые серверу разрешено публиковать.  Если поле не указано или пусто, регистрируются все встроенные инструменты.  Используется, чтобы открыть узкое подмножество (например, для сервера инвентаризации только для чтения).|
|`enabled_prompts`|Массив имен промптов.  Та же семантика, что и у `enabled_tools`, но для промптов.|

<br/>

Пример - сервер, который публикует только `server_info` и `list_providers`:

```json
{
  "server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true},
  "enabled_tools": ["server_info", "list_providers"]
}
```

### Поддержка ревизий протокола {#protocol-revision-support}

Ревизия протокола `2026-07-28`, `server.stateless` и формат журнала аудита `otel` доступны в StackQL `v0.11.660` и более поздних версиях.  `server.protocol_version` и флаг `--mcp.protocol.version` доступны в StackQL `v0.12.732` и более поздних версиях.

Сервер работает со всеми ревизиями Model Context Protocol, которые поддерживает [Go MCP SDK](https://github.com/modelcontextprotocol/go-sdk), и согласовывает ревизию отдельно с каждым клиентом, поэтому с одним сервером может работать парк разнородных клиентов.

| Ревизия | Жизненный цикл | Запрос подтверждения (`safe` / `delete_safe`) |
|--|--|--|
|`2026-07-28` (объявляется)|Без рукопожатия: `server/discover`, затем каждый запрос передает `io.modelcontextprotocol/protocolVersion` и `io.modelcontextprotocol/clientCapabilities` в `_meta` (а по HTTP также заголовки `Mcp-Protocol-Version`, `Mcp-Method` и `Mcp-Name`).|Результат `input_required`; клиент повторяет вызов с `inputResponses` (SEP-2322).|
|`2025-11-25`, `2025-06-18`|Рукопожатие `initialize` / `notifications/initialized`.|Запрос `elicitation/create`, инициированный сервером.|
|`2025-03-26`, `2024-11-05`|Как и выше.|Как и выше.|

<br />

**stdio** обслуживает все ревизии в одном процессе: первый запрос клиента `2026-07-28` обслуживается без рукопожатия, а `initialize` от более старого клиента по-прежнему работает.  Для Claude Desktop, средств запуска npm / PyPI и образа Docker ничего настраивать не нужно.

**Streamable HTTP** по умолчанию использует модель с сохранением состояния и отдельным сеансом для каждого клиента (`Mcp-Session-Id`), которую SDK обслуживает для ревизий до `2025-11-25`.  На запрос `2026-07-28` сервер отвечает ошибкой JSON-RPC `-32022` (неподдерживаемая версия протокола; в выпусках до `v0.12.718` - обычный HTTP 400), поле `data.supported` которой перечисляет ревизии с рукопожатием, и `server/discover` объявляет то же самое, поэтому клиент переходит на более раннюю ревизию, а существующие интеграции по HTTP сохраняют свои сеансы и запросы подтверждения без изменений.  Чтобы обслуживать `2026-07-28` по HTTP напрямую, задайте `server.stateless` (или закрепите ревизию `2026-07-28`, см. [ниже](#pinning-the-revision)):

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true, "stateless": true}}'
```

Сервер без сеанса не выдает `Mcp-Session-Id`, отвечает на `GET` и `DELETE` кодом 405 (сеанса, который нужно завершить, нет), сохраняет `tools/list`, `prompts/list` и `resources/list` неизменными для всех подключений и проводит цикл подтверждения через `input_required`.  Он по-прежнему принимает `initialize` от более старого клиента и обслуживает его операции чтения, но не может сохранить возможность elicitation, которую этот клиент объявил при инициализации (каждый запрос получает временный сеанс), поэтому на сервере без сеанса более старые клиенты не могут дать подтверждение для операций записи, которые его требуют.  Выбирайте `stateless` для хостов с текущей ревизией, а значение по умолчанию - для парка, в котором еще есть более старые клиенты.

Сервер не хранит состояние между вызовами: режим, аудит и учетные данные провайдеров - это конфигурация уровня процесса, поэтому ничего не нужно переносить за явные дескрипторы.

#### Закрепление ревизии {#pinning-the-revision}

По умолчанию сервер объявляет все поддерживаемые ревизии и согласовывает ревизию с каждым клиентом.  Флаг `--mcp.protocol.version` или `server.protocol_version` в объекте конфигурации (приоритет имеет флаг) задает самую новую объявляемую ревизию:

```bash
# sessionless only; stateless Streamable HTTP is implied
stackql mcp \
  --mcp.server.type=http \
  --mcp.protocol.version=2026-07-28 \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true}}'

# handshake lifecycle only
stackql mcp --mcp.server.type=stdio --mcp.protocol.version=2025-11-25
```

| Значение | Объявляется | Действие |
|--|--|--|
|`auto` (по умолчанию) или не задано|Все поддерживаемые ревизии.|Согласование, как описано выше: самая высокая ревизия, которую поддерживают обе стороны.|
|`2026-07-28`|Только `2026-07-28`.|Только без сеанса, и для Streamable HTTP подразумевается `stateless`.  На `initialize` от более старого клиента сервер отвечает `2025-11-25` - это сигнал клиенту отключиться, а не читать ответ как новый жизненный цикл.|
|`2025-11-25` (или любая более старая ревизия)|Эта ревизия и все предыдущие.|Только жизненный цикл с рукопожатием: запрос `2026-07-28` получает ошибку JSON-RPC `-32022`, в которой `data.supported` перечисляет объявляемые ревизии, чтобы клиент мог повторить согласование.  Более старые клиенты с рукопожатием сохраняют свою ревизию.|

<br />

Любое другое значение не проходит проверку допустимости конфигурации при запуске, и ошибка называет допустимые значения.

#### Ограничения транспорта {#transport-limits}

Тело запроса Streamable HTTP ограничено 4 MiB (сверх этого - HTTP 413), JSON с вложенностью глубже 1000 уровней отклоняется до синтаксического анализа, а один кадр `stdio` ограничен 8 MiB.  Ни одно из этих ограничений не настраивается; все они намного превышают размер любой SQL-инструкции, которую принимает сервер.

### (Повторная) загрузка учетных данных (`--env.file` + `reload_credentials`) {#credential-resourcing---envfile--reload_credentials}

:::note

`--env.file` и инструмент `reload_credentials` доступны в выпусках StackQL после `v0.10.542`.

:::

Блок переменных среды процесса фиксируется при его запуске.  Это создает две проблемы для MCP-серверов:

- MCP-сервер `stdio`, запущенный настольным клиентом (Claude Desktop, Cursor и т. д.) без переменных среды с учетными данными, никогда их не увидит - клиент передает дочернему процессу собственную среду.
- Смененные краткосрочные учетные данные никогда не попадают в долго работающий сеанс сервера.

Флаг `--env.file` устраняет оба пробела: он указывает файл в стиле dotenv, который служит изменяемым хранилищем учетных данных:

```bash
stackql mcp --mcp.server.type=stdio --env.file /path/to/stackql-credentials.env
```

#### Семантика загрузки {#sourcing-semantics}

Файл загружается в среду процесса при запуске для каждой точки входа (`exec`, `shell`, `srv`, `registry`, `mcp`):

- Если флаг пуст или не задан, ничего не происходит - учетные данные определяются лениво из среды процесса во время запроса, в точности как раньше.
- Отсутствие файла по указанному пути допускается и ни к чему не приводит (файл может быть создан позже).
- Неправильно сформированный или нечитаемый файл вызывает неустранимую ошибку при запуске.
- Задаются только ключи с непустыми значениями; существующие переменные среды процесса **перезаписываются** (файл - источник истины); значения никогда не сбрасываются.
- Флаг задается только в командной строке - он не загружается из `.stackqlrc`.

Формат файла - одна пара `KEY=VALUE` на строку.  Допускаются комментарии `#`, пустые строки, необязательный префикс `export `, необязательные одинарные или двойные кавычки вокруг значения и окончания строк CRLF:

```bash
# stackql-credentials.env
export OKTA_SECRET_KEY="00abc...xyz"
STACKQL_GITHUB_USERNAME=myuser
STACKQL_GITHUB_PASSWORD='ghp_mytoken'
```

#### `reload_credentials` {#reload_credentials}

Инструмент [`reload_credentials`](/mcp/reload_credentials) повторно загружает файл `--env.file` в среду процесса посреди сеанса, а затем сообщает статус определения учетных данных для каждого провайдера.  Значения секретов никогда не возвращаются, не записываются в журнал и не попадают в аудит - только имена и статусы.  Без настроенного `--env.file` инструмент сводится к простой проверке статуса.

Если запрос завершается ошибкой при определении учетных данных, ошибка MCP содержит подсказку, которая предлагает агенту вызвать `reload_credentials` и повторить попытку, поэтому агентные клиенты восстанавливаются сами: запишите учетные данные в файл, попросите агента выполнить перезагрузку, и неудавшийся запрос выполнится при повторной попытке - перезапуск сервера не нужен.

`reload_credentials` не поддерживается в режиме бэкенда `reverse_proxy` - запросы выполняются в процессе удаленного сервера stackql, поэтому инструмент возвращает ошибку, которая предлагает пользователю выполнить перезагрузку на базовом сервере.

#### Windows и Claude Desktop {#windows-and-claude-desktop}

`setx` записывает значения в реестр, а не в запущенные процессы, а Claude Desktop передает дочерним MCP-процессам собственную (неактуальную) среду - поэтому изменения учетных данных обычно требуют полного перезапуска Claude Desktop.  С `--env.file` файл учетных данных можно создать или сменить в любой момент, и `reload_credentials` подхватит его без перезапуска.  Пример готовой конфигурации см. на странице [Использование StackQL с Claude Desktop](/getting-started/claude-desktop).

### Аутентификация HTTP-клиентов {#http-client-authentication}

:::note

`server.auth_token_env_var` и `server.allow_unauthenticated` доступны в StackQL `v0.12.742` и более поздних версиях.

:::

Транспорт HTTP требует аутентификации клиентов.  `server.auth_token_env_var` задает имя переменной среды, в которой хранится заранее согласованный токен bearer; каждый запрос должен содержать `Authorization: Bearer <token>`, иначе на него приходит ответ `401`.  Токен читается из среды, поэтому он никогда не появляется в `--mcp.config` или в аргументах процесса.

```bash
export STACKQL_MCP_TOKEN="$(openssl rand -hex 32)"

stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "auth_token_env_var": "STACKQL_MCP_TOKEN"}}'
```

:::info[Требуется аутентификация на сервере]

Работа без токена включается только явно: задайте `"allow_unauthenticated": true` в `server`.  Если не задан ни один из ключей, сервер завершает работу при запуске с сообщением, в котором названы оба; он также завершает работу, если переменная с токеном не задана или пуста.  Начиная с выпуска `v0.12.742` при использовании транспорта `http` необходимо добавить в `server` либо `auth_token_env_var`, либо `"allow_unauthenticated": true`.

:::

TLS (`tls_cert_file` / `tls_key_file`) шифрует транспорт, но не аутентифицирует клиента; для любого прослушивателя за пределами loopback используйте его вместе с токеном.  Запросы браузера между источниками (несовпадающий `Origin` или межсайтовый `Sec-Fetch-Site`) отклоняются с кодом `403` независимо от аутентификации.  Поставляемый в комплекте `stackql_mcp_client` не отправляет заголовок `Authorization`, поэтому сервер, с которым он работает, должен явно включить работу без аутентификации.

Начиная с `v1.0` запуск сервера с [`--access.config`](/command-line-usage/access-management) заменяет проверку общего токена аутентификацией каждой вызывающей стороны: каждый HTTPS-запрос проверяется по настроенной схеме (JWT, статический токен bearer или взаимный TLS) и авторизуется по правилам политики.  В этом случае TLS на сервере обязателен, аутентификация `local_os` по HTTP отклоняется, а запрос без учетных данных никогда не переходит к токену из среды сервера.  Управление доступом недоступно с типом сервера `reverse_proxy`.

### Режимы сервера {#server-modes}

`server.mode` выбирает один из четырех контрактов безопасности.  Все четыре разрешают `SELECT` и чтение метаданных; они различаются тем, как обрабатывают изменения данных и операции жизненного цикла.

| Режим | `SELECT` / метаданные | `INSERT` / `UPDATE` / `REPLACE` | `DELETE` | `EXEC` (жизненный цикл) |
|--|--|--|--|--|
|`read_only`|разрешено|отклонено|отклонено|отклонено|
|`safe` (по умолчанию)|разрешено|требуется подтверждение|требуется подтверждение|требуется подтверждение|
|`delete_safe`|разрешено|разрешено|требуется подтверждение|требуется подтверждение|
|`full_access`|разрешено|разрешено|разрешено|разрешено|

<br />

**Отклонено** - клиенту сразу возвращается ошибка.

**Требуется подтверждение** - используется поток elicitation MCP, форма которого зависит от согласованной [ревизии протокола](#protocol-revision-support):

- Если клиент объявил возможность elicitation (при инициализации или в возможностях клиента в `_meta` каждого запроса для `2026-07-28`), сервер просит пользователя подтвердить действие коротким сообщением (имя инструмента, класс запроса, SQL).  В `2026-07-28` запрос подтверждения возвращается как результат `input_required` с запросом входных данных `elicitation/create` под идентификатором `stackql_approval`, и клиент повторяет вызов с ответом в `inputResponses`; в более ранних ревизиях сервер сам отправляет запрос `elicitation/create` посреди вызова.  Пользователь принимает, отклоняет или отменяет действие.
- Если клиент **не** объявил elicitation, вызов инструмента отклоняется с сообщением, которое объясняет причину и указывает оператору на режим `full_access`.

На запрос подтверждения отвечает клиент, поэтому подтверждение защищает от действий агента без ведома его пользователя, а не от недоверенной вызывающей стороны.  Если вызывающим сторонам нельзя доверять, используйте транспорт HTTP вместе с [аутентификацией клиентов](#http-client-authentication).

Режим глобален для сервера.  Переопределения для отдельных инструментов нет.

Начиная с `v1.0` [`run_select_query`](/mcp/run_select_query) отклоняет `INSERT`, `UPDATE`, `REPLACE`, `DELETE` и `EXEC` в любом режиме, включая `full_access`; ошибка называет `run_mutation_query` или `run_lifecycle_operation`.  Кроме того, каждый инструмент имеет `title` и четыре поведенческие подсказки MCP в виде явных логических значений (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`), выведенные из той же классификации, которую применяет контроль политик.  `openWorldHint` равно `true` для `list_registry`, `pull_provider`, `run_select_query`, `run_mutation_query` и `run_lifecycle_operation`, которые обращаются к конечным точкам реестра или провайдеров, и `false` для инструментов, которые читают только локальное состояние.  Подсказки носят рекомендательный характер для пользовательского интерфейса клиента; принудительное применение остается за контролем политик.

:::info[Контроль полезной нагрузки]

Начиная с выпуска `v0.12.742` полезная нагрузка из нескольких инструкций в любом режиме контролируется по самой привилегированной из них, поэтому `SELECT 1; DELETE ...` обрабатывается как `DELETE`, а запись аудита содержит `query_class` `mutation_delete`.  `validate_select_query` принимает ровно одну инструкцию.

:::

#### Изменение поведения режима по умолчанию {#default-mode-behaviour-change}

Предыдущие выпуски обеспечивали безопасность только с помощью единственного флага `read_only: true/false`, значением по умолчанию которого было "без ограничений".  Текущее значение по умолчанию (`mode: safe`) сразу требует подтверждения пользователя для изменений данных.  Операторы, использующие MCP-клиент с поддержкой elicitation (Claude Desktop, Cursor, Continue и т. д.), увидят один запрос подтверждения на каждое изменение данных.  Операторы, использующие автоматизацию или поставляемый в комплекте `stackql_mcp_client` (который не объявляет elicitation), должны явно включить менее строгий режим: `mode: delete_safe`, чтобы выполнять `INSERT`, `UPDATE` и `REPLACE`, или `mode: full_access`, чтобы также выполнять `DELETE` и операции жизненного цикла.

Прежний ключ JSON / YAML `read_only: true` по-прежнему принимается для обратной совместимости и считается эквивалентным `mode: read_only`.

#### Примеры {#examples}

```bash
# Read-only: SELECTs proceed; mutations and lifecycle refused immediately.
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true, "mode": "read_only"}}'

# Delete-safe: INSERT/UPDATE/REPLACE proceed; DELETE and EXEC need approval.
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true, "mode": "delete_safe"}}'

# Full access: everything proceeds without prompting.  Use only with trusted
# clients and operators.
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true, "mode": "full_access"}}'
```

### Журнал аудита {#audit-log}

Каждый вызов инструмента записывает одну запись в настроенное место назначения аудита - по умолчанию в формате JSONL или в виде записей журнала OpenTelemetry (см. [Формат журнала](#log-format)).  Аудит **включен по умолчанию**.  Аудит отвечает на вопрос "что сделал агент", а не "что увидел агент" - строки результатов инструкций `SELECT` намеренно не записываются ни в одном из форматов.

#### Что записывается {#what-gets-recorded}

| Поле | Описание |
|--|--|
|`timestamp`|Фактическое время начала вызова (RFC3339).|
|`tool`|Имя инструмента (например, `run_select_query`).|
|`mode`|Режим сервера, действующий в момент вызова.|
|`decision`|`allow` / `refuse_immediate` / `needs_approval_accepted` / `needs_approval_declined` / `needs_approval_cancelled` / `needs_approval_unavailable`.|
|`query_class`|`select` / `mutation_create` / `mutation_delete` / `lifecycle` / `unknown`.  Для полезной нагрузки из нескольких инструкций - класс самой привилегированной из них.|
|`sql`|Строка SQL для инструментов запросов (`run_select_query`, `run_mutation_query`, `run_lifecycle_operation`, `validate_select_query`).|
|`args`|Поля иерархии для инструментов метаданных (`list_*`, `describe_method`); SQL + `row_limit` для инструментов запросов.|
|`duration_ms`|Фактическая длительность контроля + обработчика.|
|`error`|Сообщение об ошибке, если инструмент завершился ошибкой или вызов был отклонен.|

<br />

Строки результатов инструкций `SELECT` намеренно исключаются - они могут быть очень большими и содержать конфиденциальные данные.

#### Файловое место назначения {#file-sink}

Сейчас поставляется только одно место назначения - `file`.  Один JSON-объект на строку, fsync после каждой записи, ротация в стиле lumberjack по размеру / возрасту / количеству резервных копий.

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{
    "server": {
      "transport": "http",
      "address": "127.0.0.1:9912",
      "allow_unauthenticated": true,
      "audit": {
        "file": {
          "path": "/var/log/stackql-mcp.log",
          "max_size_mb": 100,
          "max_backups": 5,
          "max_age_days": 30
        }
      }
    }
  }'
```

Расположение можно указать двумя способами:

- `audit.file.path` - полный путь к файлу (абсолютный или относительно текущего рабочего каталога).
- `audit.file.dir` - каталог; место назначения выбирает в нем базовое имя `stackql_mcp_server_<RFC3339-utc-second>.log`.

Если ни один из параметров не задан в `mcp.config`, MCP-сервер по умолчанию использует в качестве `dir` текущий рабочий каталог, поэтому для существующих операторов поведение не меняется.  Сам базовый универсальный пакет мест назначения отказывается молча выбирать каталог - решение "куда попадают журналы" всегда принимает вызывающая сторона.

Итоговый абсолютный путь выводится в stderr при запуске в виде `sink file: /path/to/file.log`.

#### Формат журнала {#log-format}

У потока аудита две кодировки, которые записываются в одно и то же файловое место назначения:

```bash
stackql mcp --mcp.server.type=stdio --mcp.log.format=jsonl   # default, unchanged
stackql mcp --mcp.server.type=stdio --mcp.log.format=otel    # OTLP/JSON log records
```

Флаг переопределяет `server.audit.format` в `mcp.config` (`"audit": {"format": "otel"}`).  `jsonl` побайтно совместим с записями, описанными выше.  `otel` записывает один объект OTLP/JSON `LogsData` на строку - в той форме, которую приемник `otlp_json_file` в OpenTelemetry Collector принимает как есть (проверено с otelcol-contrib 0.160.0), поэтому поток попадает в любой конвейер OTLP без процессора преобразования:

```yaml
receivers:
  otlp_json_file:
    include: [/var/log/stackql-mcp.log]
exporters:
  debug: {}
service:
  pipelines:
    logs:
      receivers: [otlp_json_file]
      exporters: [debug]
```

Каждый вызов инструмента создает одну запись журнала; вызов, прошедший контроль подтверждения, создает вторую запись для решения elicitation.  Записи одного вызова имеют общие `gen_ai.tool.call.id` и идентификатор трассировки.  Значение W3C `traceparent`, переданное вызывающей стороной в `params._meta`, учитывается; в противном случае для каждого MCP-сеанса генерируется один идентификатор трассировки, чтобы записи сеанса агента можно было сопоставить.

Набор выдаваемых атрибутов - версионируемый интерфейс: область инструментирования - `github.com/stackql/stackql/pkg/mcp_server/audit` версии `1.0.0`, а `schemaUrl` закрепляет стабильные соглашения на `https://opentelemetry.io/schemas/1.44.0`.  Атрибуты `gen_ai.*` и `mcp.*` следуют семантическим соглашениям [GenAI](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md#execute-tool-span) и [MCP](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md), которые находятся в статусе Development; версия области повышается при изменении набора.

| Атрибут | Запись | Значение |
|--|--|--|
|`service.name`, `service.version`|ресурс|`stackql`, версия StackQL|
|`gen_ai.operation.name`|вызов инструмента|`execute_tool`|
|`mcp.method.name`|обе|`tools/call` в записи вызова инструмента, `elicitation/create` в записи решения|
|`gen_ai.tool.name`|обе|Имя инструмента|
|`gen_ai.tool.call.id`|обе|Генерируется для каждого вызова, общий для обеих записей|
|`mcp.protocol.version`|обе|Согласованная ревизия|
|`mcp.session.id`|обе|Идентификатор сеанса (отсутствует для HTTP-запросов без сеанса)|
|`stackql.mode`|обе|Режим сервера|
|`stackql.decision`|обе|Значение `decision` из таблицы выше|
|`stackql.query`|вызов инструмента|Дословный SQL, для инструментов запросов|
|`stackql.query_class`|вызов инструмента|Значение `query_class`|
|`stackql.provider`|вызов инструмента|Провайдер, для инструментов метаданных|
|`stackql.query.source`|вызов инструмента|Идентификатор записи Query Library, если он передан|
|`stackql.duration_ms`|вызов инструмента|Фактическая длительность|
|`stackql.rows_returned`|вызов инструмента|Количество строк, для инструментов, возвращающих строки|
|`error.type`, `error.message`|вызов инструмента|При сбое: решение об отклонении или `tool_error` после контроля|

<br />

Тело записи - `execute_tool <tool>` / `elicitation <tool>`; уровень серьезности - `INFO` или `ERROR`, если вызов завершился сбоем или был отклонен.  Контракт скрытия данных одинаков в обоих форматах: значения результатов никогда не сериализуются, только инструкция, которая их вернула.

#### Режимы обработки сбоев {#failure-modes}

Если место назначения возвращает ошибку, поведение ответа зависит от `audit.failure_mode`.

| failure_mode | Действие |
|--|--|
|`strict` (по умолчанию)|Вызов инструмента возвращает клиенту ошибку аудита, даже если сам инструмент выполнился успешно.  Это сделано намеренно: лучше неоднозначный ответ клиенту, чем незамеченный `DELETE`.|
|`strict_mutations`|`SELECT` / чтение метаданных выполняются с примечанием в stderr; изменения данных и операции жизненного цикла возвращают ошибку аудита.|
|`best_effort`|Всегда записывать в stderr и продолжать.|

#### Последовательность {#sequencing}

Запись аудита происходит **после** выполнения инструмента (или его отклонения контролем), но **до** возврата ответа клиенту.  В режиме strict сбой записи аудита при успешном DELETE означает, что строка удалена, но клиент получает ошибку - так задумано, чтобы ни одно изменение данных не прошло без аудита.

#### Отключение аудита {#disabling-audit}

Чтобы полностью отключить аудит, как в выпусках до `v0.10.474`, в которых аудита не было:

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true, "audit": {"disabled": true}}}'
```

Каждый возвращает и текстовое отображение (для LLM), и типизированную структурированную полезную нагрузку (для программных клиентов). |[`query_library_search`](/mcp/query_library_search)|Таблица|Поиск отобранных шаблонов запросов по намерению на естественном языке. Только чтение; записи с изменением данных требуют явного включения и исключаются в режиме `read_only`.|`intent`, `provider?`, `service?`, `tags?`, `include_mutations?`, `limit?`|
|[`query_library_get`](/mcp/query_library_get)|KV|Получение шаблона и объявлений его параметров. При непустом `params` - проверка значений и возврат сформированного SQL вместе с `next_tool` без выполнения.|`id`, `params?`|
|[`validate_select_query`](/mcp/validate_select_query)|KV|Синтаксический анализ и планирование одной инструкции `SELECT` без выполнения.  Возвращает `{valid, errors}`.  Только `SELECT`; ровно одна инструкция.|`sql`|
|[`run_select_query`](/mcp/run_select_query)|Таблица|Выполнение `SELECT`.  Возвращает `{rows}`.  Только чтение.|`sql`, `row_limit?`|
|[`run_mutation_query`](/mcp/run_mutation_query)|KV|Выполнение `INSERT`/`UPDATE`/`REPLACE`/`DELETE` в провайдере.  **Реальные побочные эффекты.** Возвращает `{messages, timestamp}`.  Контролируется [режимом](#server-modes) сервера.|`sql`|
|[`run_lifecycle_operation`](/mcp/run_lifecycle_operation)|KV|Выполнение операции жизненного цикла stackql `EXEC`.  Возвращает `{messages, timestamp}`.  Контролируется [режимом](#server-modes) сервера.|`sql`|
|[`list_registry`](/mcp/list_registry)|Таблица|Провайдеры (и их версии), доступные в настроенном реестре.  В отличие от `list_providers`, который выводит только уже загруженные провайдеры.|`provider?`|
|[`pull_provider`](/mcp/pull_provider)|KV|Установка одного провайдера из реестра в локальный кэш.  Только состояние локального кэша - без влияния на облачную плоскость управления или плоскость данных.|`provider`, `version?`|
|[`reload_credentials`](/mcp/reload_credentials)|Таблица|Повторная загрузка учетных данных из файла dotenv `--env.file` в среду процесса и отчет о статусе их определения для каждого провайдера (`ok`, `unresolved`, `not_checked`).  Никогда не возвращает значения секретов.  Разрешено во всех режимах.|`provider?`|

Прежде чем писать SQL с нуля, обратитесь к `query_library_search`, а затем используйте `query_library_get`, чтобы изучить подходящий шаблон и сформировать из него SQL. Инструменты запросов также принимают необязательный параметр `source` с идентификатором записи библиотеки - только для указания источника; выполнение по-прежнему подчиняется обычному режиму сервера и политике подтверждения.

:::note

`describe_resource` выведен из эксплуатации в StackQL `v0.12.732`; MCP-клиенты, промпты или указания для агентов, которые его вызывали, должны вместо этого вызывать [`list_methods`](/mcp/list_methods), а затем `describe_method`.  У ресурса нет единого списка полей, поскольку каждый метод доступа возвращает собственную форму данных, поэтому имена столбцов берутся из [`describe_method`](/mcp/describe_method) для метода, к которому направляется запрос.  SQL-инструкция [`DESCRIBE`](/language-spec/describe) не изменилась.

:::

### Примеры {#examples-1}

#### Базовый автономный MCP-сервер {#basic-standalone-mcp-server}

Запустите автономный MCP-сервер с аутентификацией провайдера и токеном bearer для его клиентов:

```bash
export GOOGLE_CREDENTIALS=$(cat /path/to/google-credentials.json)
export STACKQL_MCP_TOKEN="$(openssl rand -hex 32)"

stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "auth_token_env_var": "STACKQL_MCP_TOKEN"}}' \
  --registry='{"url": "https://registry.stackql.app/providers"}' \
  --auth='{"google": {"type": "service_account", "credentialsfilepath": "/path/to/google-credentials.json"}}'
```

#### MCP-сервер с сервером PostgreSQL (в памяти) {#mcp-server-with-postgresql-server-in-memory}

Запустите серверы MCP и PostgreSQL для доступа по двум протоколам:

```bash
export GOOGLE_CREDENTIALS=$(cat /path/to/google-credentials.json)

stackql srv \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true}}' \
  --pgsrv.port 5665 \
  --registry='{"url": "https://registry.stackql.app/providers"}' \
  --auth='{"google": {"type": "service_account", "credentialsfilepath": "/path/to/google-credentials.json"}}'
```

#### Сервер инвентаризации только для чтения с аудитом по известному пути {#read-only-inventory-server-with-audit-to-a-known-path}

Подходит для агента инвентаризации, который никогда не должен изменять данные:

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{
    "server": {
      "transport": "http",
      "address": "127.0.0.1:9912",
      "allow_unauthenticated": true,
      "mode": "read_only",
      "audit": {"file": {"path": "/var/log/stackql-mcp-audit.log"}}
    }
  }' \
  --registry='{"url": "https://registry.stackql.app/providers"}' \
  --auth='{"google": {"type": "service_account", "credentialsfilepath": "/path/to/google-credentials.json"}}'
```

#### Сервер автоматизации с полным доступом {#full-access-automation-server}

Для доверенных конвейеров автоматизации, которым нужны изменения данных и которые не могут отвечать на запросы elicitation.  Конвейер предъявляет токен bearer, хранящийся в `STACKQL_MCP_TOKEN`:

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{
    "server": {
      "transport": "http",
      "address": "127.0.0.1:9912",
      "auth_token_env_var": "STACKQL_MCP_TOKEN",
      "mode": "full_access"
    }
  }' \
  --registry='{"url": "https://registry.stackql.app/providers"}' \
  --auth='{"google": {"type": "service_account", "credentialsfilepath": "/path/to/google-credentials.json"}}'
```

#### Защищенный MCP-сервер с TLS {#secure-mcp-server-with-tls}

Запустите MCP-сервер с шифрованием TLS в режиме обратного прокси:

Сначала сгенерируйте сертификаты TLS (самозаверенные для разработки):

```bash
openssl req -x509 -newkey rsa:4096 -keyout server_key.pem -out server_cert.pem -days 365 -nodes
```

Затем запустите сервер:

```bash
export STACKQL_MCP_TOKEN="$(openssl rand -hex 32)"

stackql srv \
  --mcp.server.type=reverse_proxy \
  --mcp.config '{
    "server": {
      "tls_cert_file": "server_cert.pem",
      "tls_key_file": "server_key.pem",
      "transport": "http",
      "address": "127.0.0.1:9004",
      "auth_token_env_var": "STACKQL_MCP_TOKEN"
    },
    "backend": {
      "dsn": "postgres://stackql:stackql@127.0.0.1:5446?default_query_exec_mode=simple_protocol"
    }
  }' \
  --pgsrv.port 5446 \
  --registry='{"url": "https://registry.stackql.app/providers"}' \
  --auth='{"google": {"type": "service_account", "credentialsfilepath": "/path/to/google-credentials.json"}}'
```

### Тестирование MCP-сервера {#testing-your-mcp-server}

Репозиторий содержит MCP-клиент для разработки (`stackql_mcp_client`), предназначенный для скриптов и регрессионных тестов.  Соберите его командой:

```bash
python cicd/python/build.py --build-mcp-client
```

В результате создается `./build/stackql_mcp_client`.

Обратите внимание, что `stackql_mcp_client` не отправляет заголовок `Authorization`, поэтому сервер, к которому он обращается, должен задавать `"allow_unauthenticated": true` (как в примерах выше); сервер, защищенный токеном, отвечает ему `401`.  Кроме того, он **не** объявляет возможность elicitation MCP - он предназначен для неинтерактивных скриптов.  На сервере `safe` он получит отказ "client does not support elicitation" для вызовов с изменением данных и операций жизненного цикла; на сервере `delete_safe` - для вызовов `DELETE` и `EXEC`.  Для интерактивного тестирования с запросами elicitation используйте MCP-клиент, встроенный в редактор (Claude Desktop, Cursor, Continue).

```bash
# List all available tools
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912

# Server identity, mode, audit / registry context
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action server_info

# Re-source the --env.file credentials file and report per-provider
# credential status - a good first diagnostic when queries fail on auth
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action reload_credentials

# List providers already pulled into the local cache
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action list_providers

# List providers (and versions) available in the registry
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action list_registry

# Install a provider from the registry into the local cache
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action pull_provider \
  --exec.args '{"provider": "kafka"}'

# List services for a provider
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action list_services \
  --exec.args '{"provider": "google"}'

# List access methods for a resource (this is how an agent finds required
# WHERE parameters before writing a query)
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action list_methods \
  --exec.args '{"provider": "google", "service": "compute", "resource": "networks"}'

# Validate a SELECT without executing
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action validate_select_query \
  --exec.args '{"sql": "select name from google.compute.networks where project = '"'"'my-project'"'"';"}'

# Execute a SELECT
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action run_select_query \
  --exec.args '{"sql": "select name from google.compute.networks where project = '"'"'my-project'"'"';"}'

# Mutation (a DELETE) - succeeds only against a full_access server:
# stackql_mcp_client does not support elicitation, so safe and delete_safe
# servers refuse it.
./build/stackql_mcp_client exec \
  --client-type=http \
  --url=http://127.0.0.1:9912 \
  --exec.action run_mutation_query \
  --exec.args '{"sql": "delete from google.compute.firewalls where project = '"'"'my-project'"'"' and firewall = '"'"'old-rule'"'"';"}'
```

### Интеграция с ИИ-ассистентами {#integration-with-ai-assistants}

Чтобы интегрировать MCP-сервер StackQL с ИИ-ассистентом, зарегистрируйте `stackql` как MCP-сервер в конфигурации ассистента.  Большинство MCP-клиентов, встроенных в редакторы, запускают сервер через `stdio`; для них используйте `--mcp.server.type=stdio`, и ассистент запускает процесс напрямую.  Автономные агенты, работающие по HTTP, могут подключаться к долго работающему процессу `stackql mcp --mcp.server.type=http`.

Сведения о Claude Desktop, включая страницу в Anthropic Connector Directory (рекомендуемый способ установки), скачиваемый MCP Bundle (`.mcpb`) и настройку вручную, см. на странице [Использование StackQL с Claude Desktop](/getting-started/claude-desktop).

:::note

Расположение файлов конфигурации зависит от операционной системы и ИИ-ассистента.  Правильный путь и формат см. в документации вашего ИИ-ассистента.

:::

### Архитектурные соображения {#architecture-considerations}

При выборе режима развертывания учитывайте следующее:

1. **Автономный (`stackql mcp`)**: самая простая настройка, идеально подходит для разработки и для клиентов, встроенных в редакторы, через `stdio`.
2. **Два сервера в памяти (`stackql srv` с `mcp.server.type=http`)**: один процесс обслуживает и MCP, и сетевой протокол PostgreSQL.  Наилучшая производительность, подходит для большинства развертываний в рабочей среде.
3. **Обратный прокси (`stackql srv` с `mcp.server.type=reverse_proxy`)**:
   - позволяет разделять рабочие нагрузки между процессами или хостами
   - поддерживает шифрование TLS для защищенных конечных точек MCP
   - позволяет независимо масштабировать интерфейсы MCP и PostgreSQL
   - обеспечивает гибкость интеграции с корпоративными центрами сертификации (примечание: поддержка корпоративных центров сертификации экспериментальная)

И отдельно о безопасности:

- Начните со значения по умолчанию `mode: safe`.  MCP-клиенты с поддержкой elicitation (Claude Desktop, Cursor, Continue) будут запрашивать подтверждение пользователя перед любым изменением данных.
- Закрепите `mode: read_only` для агентов инвентаризации или аналитики, которые никогда не должны выполнять запись.
- Закрепите `mode: delete_safe`, если нужна свобода создания и обновления, но для разрушительных операций требуется участие человека.
- Используйте `mode: full_access` только для доверенных конвейеров автоматизации и только вместе с журналом аудита, который кто-то просматривает.
- Задавайте `server.auth_token_env_var` для любого HTTP-прослушивателя, к которому могут обратиться другие процессы или хосты; `allow_unauthenticated` предназначен для локальной разработки.  Один только TLS не аутентифицирует клиентов.

:::caution

При использовании TLS с корпоративными центрами сертификации (CA) может потребоваться дополнительная настройка.  Эта возможность экспериментальная и может потребовать доработки с учетом вашей конкретной реализации CA.

:::
