Управление доступом вызывающих сторон аутентифицирует вызывающую сторону сеанса StackQL и авторизует каждую инструкцию по политике. Оно не зависит от учетных данных провайдеров, которые по-прежнему передаются через флаг `--auth`, переменные среды или [сеансы провайдеров](/getting-started/provider-sessions). По умолчанию оно отключено, и развертывания, в которых оно не включено, работают как раньше. Доступно в StackQL `v1.0` и более поздних версиях.

## Включение управления доступом {#enabling-access-management}

Управление доступом включается запуском StackQL с глобальным флагом `--access.config`, который указывает на JSON-файл конфигурации. В примере интерактивная оболочка запускается в защищенном режиме; команды `exec` и `mcp` включаются так же.

```bash
stackql --access.config '{"path": "/etc/stackql/access.json"}' shell
```

Флаг `--access.config` принимает JSON-конверт с единственным ключом `path`; также принимается просто путь к файлу. Конфигурация загружается один раз при запуске, поэтому выполняйте смену ключей или политики через контролируемый перезапуск.

Пока управление доступом включено, работают только команды `exec`, `shell`, `mcp` и `version`; другие команды, включая `registry`, отказываются выполняться, а не обходят защищенный путь. Команда `srv` и тип MCP-сервера `reverse_proxy` также отказываются работать, поскольку зависимость, реализующая сетевой протокол PostgreSQL, пока не предоставляет сведения об аутентификации для каждого подключения. SQL-инструкции `AUTH` и `AUTH REVOKE` в защищенном режиме отклоняются; вместо этого задавайте учетные данные провайдеров через конфигурацию хоста. Защищенная команда `exec`, завершившаяся ошибкой, возвращает код завершения `1` после вывода ошибки.

## Режимы аутентификации {#authentication-modes}

В файле конфигурации выбирается одно значение `type`: `jwt` (по умолчанию, если не указано), `bearer`, `mtls` или `local_os`. Конфигурация - это строгий JSON: неизвестные поля и поля, относящиеся к другому режиму, отклоняются. Все режимы используют одни и те же правила `rules` и один и тот же [каталог субъектов](#principal-directory).

### JWT {#jwt}

Вызывающая сторона предъявляет подписанный токен, который проверяется без обращения к сети по ключам, закрепленным в конфигурации. Минимальная конфигурация указывает издателя и аудиторию, которые должен содержать токен, перечисляет один открытый ключ и разрешает участникам группы `analysts` выполнять инструкции чтения (участники группы `readers` могут делать это без правила, см. [Правила политики](#policy-rules)):

```json
{
  "type": "jwt",
  "issuer": "https://identity.example",
  "audience": "stackql",
  "keys": [
    {"kid": "primary", "algorithm": "EdDSA", "public_key_pem": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n"}
  ],
  "rules": [
    {"subject": "group:analysts", "resource": "host/sql/read", "action": "execute"}
  ]
}
```

Издатель, аудитория и открытые ключи закрепляются в конфигурации; обнаружение OIDC не выполняется. Допустимые алгоритмы: `EdDSA`, `RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`, `ES256`, `ES384` и `ES512`; длина ключей RSA должна быть не меньше 2048 бит. Каждый ключ привязан к своему настроенному алгоритму. Токены с неизвестным идентификатором ключа, недействительной подписью, без срока действия или с истекшим сроком действия, со значением `nbf` или `iat` в будущем либо с неверным издателем или аудиторией отклоняются. Утверждения о группах и URL-адреса, содержащиеся в токене, не используются ни для доверия, ни для членства в каталоге.

### Статический токен bearer {#static-bearer-token}

Вызывающая сторона предъявляет непрозрачный токен, а в конфигурации перечислен дайджест SHA-256 каждого принимаемого токена вместе с субъектом, который этот токен идентифицирует. Этот режим подходит для небольшого фиксированного набора удостоверений сервисов, когда запускать издателя токенов нецелесообразно:

```json
{
  "type": "bearer",
  "issuer": "local-tokens",
  "tokens": [{"subject": "alice", "sha256": "<64 hexadecimal characters: the SHA-256 of the token>"}],
  "rules": [{"subject": "group:analysts", "resource": "host/sql/read", "action": "execute"}]
}
```

В конфигурации указывается только дайджест SHA-256 каждого токена, и дайджесты должны быть уникальными. Изменение настроенных дайджестов требует перезапуска.

### Взаимный TLS {#mutual-tls}

Вызывающая сторона идентифицируется по клиентскому сертификату, который она предъявляет в HTTPS-транспорте MCP. Конфигурация содержит центр сертификации (CA), который должен был выдать сертификат, и указывает, в каком альтернативном имени субъекта содержится удостоверение:

```json
{
  "type": "mtls",
  "issuer": "client-certificates",
  "client_ca_pem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "certificate_identity": "uri_san",
  "rules": [{"subject": "group:analysts", "resource": "host/sql/read", "action": "execute"}]
}
```

Цепочка клиентского сертификата проверяется по значению `client_ca_pem`, а субъект удостоверения берется ровно из одного SAN настроенного вида: `uri_san` или `dns_san`. Резервного варианта с Common Name нет. Взаимный TLS доступен только в HTTPS-транспорте MCP.

### Удостоверение локальной ОС {#local-os-identity}

Учетные данные не передаются: субъект - это удостоверение операционной системы, от имени которого работает процесс StackQL. Конфигурации нужны только метка `issuer` и правила:

```json
{
  "type": "local_os",
  "issuer": "this-host",
  "rules": [{"subject": "group:analysts", "resource": "host/sql/read", "action": "execute"}]
}
```

Субъект удостоверения - это эффективный UID в Unix или SID в Windows процесса StackQL, включая числовые UID контейнеров без записи в passwd. Учетные данные не предъявляются, а переменная `STACKQL_CALLER_TOKEN` игнорируется. Этот режим только локальный: для вызывающих сторон по HTTP он отклоняется. Членство в группах операционной системы не предоставляет доступ; его предоставляет только членство в каталоге.

### Крайний срок сеанса {#session-deadline}

По умолчанию у запросов нет крайнего срока, связанного с аутентификацией. Учетные данные проверяются, а членство в каталоге обновляется для каждой новой инструкции, поэтому с истекшими учетными данными нельзя начать новую работу, но истечение срока не прерывает уже авторизованную инструкцию. Задайте `"enforce_session_deadline": true`, чтобы отменять выполнение по истечении `max_session_seconds` (по умолчанию `300`, максимум `86400`); этот срок сокращается до истечения срока действия JWT или сертификата. Токены при этом не продлеваются.

## Каталог субъектов {#principal-directory}

Удостоверения сопоставляются с субъектами, а субъекты - с группами в четырех таблицах настроенного бэкенда SQLite или PostgreSQL:

| Таблица | Содержимое |
|--|--|
| `stackql_access_principals` | Идентификатор субъекта и JSON-объект строковых атрибутов. Атрибут `tenant` задает пространство имен для состояния IaC предварительной версии. |
| `stackql_access_identities` | Проверенная пара `(issuer, subject)`, сопоставленная с идентификатором субъекта. |
| `stackql_access_groups` | Идентификаторы групп. |
| `stackql_access_memberships` | Привязки субъектов к группам. |

Прежде чем обслуживать защищенные запросы, создайте таблицы, удостоверения и записи о членстве через доверенное подключение для администрирования базы данных:

```sql
INSERT INTO stackql_access_principals (id, attributes) VALUES ('alice', '{}');
INSERT INTO stackql_access_groups (id) VALUES ('readers');
INSERT INTO stackql_access_identities (issuer, subject, principal_id)
VALUES ('https://identity.example', 'alice', 'alice');
INSERT INTO stackql_access_memberships (principal_id, group_id) VALUES ('alice', 'readers');
```

Используйте фактические издателя и субъекта для режима: для удостоверения локальной ОС это может быть `('this-host', '1000')`, а для взаимного TLS - `('client-certificates', 'spiffe://example/alice')`. Выберите бэкенд явно:

```bash
stackql --access.config '{"path":"/etc/stackql/access.json"}' \
  --sqlBackend '{"dbEngine":"postgres_tcp","dsn":"postgres://runtime@localhost/stackql?sslmode=require","sqlDialect":"postgres"}' \
  exec 'SELECT whoami(), groups();'
```

Каталог создает неизменяемый снимок для каждой инструкции. Отзыв доступа - это инструкция `DELETE FROM stackql_access_memberships` в подключении для администрирования; следующая инструкция видит новый снимок. Неизвестные удостоверения, отсутствующая схема, неправильно сформированные данные и сбои каталога всегда приводят к отказу в доступе. Обычный защищенный SQL не может обращаться к таблицам каталога. Выполняйте операции записи членства только через подключение для администрирования, защищайте файл базы данных и используйте отдельные привилегии базы данных для администрирования и для среды выполнения, если бэкенд это поддерживает.

## Правила политики {#policy-rules}

Каждое правило предоставляет одно действие `action` над одним ресурсом `resource` субъекту `subject` вида `group:<group id>`. Используйте скомпилированные идентификаторы методов и операций из доверенных документов провайдеров; подстановочный знак операции предоставляет не только чтение, но и методы, изменяющие данные.

Группа `readers` неявно обладает возможностью хоста выполнять безопасное чтение через SQL. Чтение субъектами вне этой группы требует `host/sql/read`, а другие инструкции требуют `execute` на `host/sql/<statement kind>`. Операции провайдеров и использование учетных данных всегда требуют явных правил, а предоставление доступа к коллекции не предоставляет доступ к ее базовым методам. Дополнительные проверки хоста:

| Ресурс | Действие | Область |
|--|--|--|
| `host/sql/read` | `execute` | Инструкции чтения вне неявной группы читателей |
| `host/sql/exec` | `execute` | Нативная инструкция `EXEC`, включая вложенную `EXEC` |
| `host/iac/run`, `host/iac/destroy` | `execute` | Отношения IaC предварительной версии, несмотря на их синтаксис `SELECT` |
| `host/function/<name>` | `execute` | Функции вне небольшого списка разрешенных заведомо чистых функций |
| `host/backend` | `read` | Непрозрачные хранимые и внешние отношения бэкенда |
| `host/credentials` | `reload` | MCP-инструмент `reload_credentials` |
| `session/variables` | `read` | Разыменование [переменных сеанса](/getting-started/session-variables) и секретов |
| `session/config` | `write` | `SET` и `UNSET` |

Раскрытие хранимых запросов проверяется перед выполнением, а повторное использование кэша планов и строк на защищенных путях отключено.

## Точки входа {#entry-points}

| Аутентификация | `exec`, `shell`, MCP через stdio | MCP через HTTPS |
|--|--|--|
| JWT | Переменная среды `STACKQL_CALLER_TOKEN` | Заголовок запроса `Authorization: Bearer` |
| Статический токен bearer | Переменная среды `STACKQL_CALLER_TOKEN` | Заголовок запроса `Authorization: Bearer` |
| Локальная ОС | Эффективный UID или SID процесса; без учетных данных | Отклоняется |
| Взаимный TLS | Отклоняется: нет проверенного TLS-подключения | Проверенная клиентская цепочка и один настроенный SAN |

Передавайте локальные учетные данные в виде токена через среду процесса, а не в виде SQL-литерала или аргумента командной строки. Через HTTPS проверка вызывающей стороны заменяет общую проверку токена bearer через `auth_token_env_var`, описанную в разделе [Аутентификация HTTP-клиентов](/command-line-usage/mcp#http-client-authentication); настройка TLS-сертификата и ключа сервера обязательна, а запрос без учетных данных никогда не переходит на токен из среды сервера в качестве резервного варианта.

## Проверка вызывающей стороны {#inspecting-the-caller}

В аутентифицированном сеансе функция `whoami()` возвращает идентификатор субъекта, а `groups()` - группы каталога в виде JSON-массива:

```sql
SELECT whoami() AS principal, groups() AS memberships;
```

```
|-----------|-------------|
| principal | memberships |
|-----------|-------------|
| alice     | ["readers"] |
|-----------|-------------|
```

Обе функции требуют сеанса, запущенного с флагом `--access.config`.

## Пошаговые руководства {#walkthroughs}

Репозиторий StackQL содержит [четыре исполняемых пошаговых руководства](https://github.com/stackql/stackql/blob/main/docs/examples/access-management/README.md), по одному на каждый режим аутентификации; их выполняет скрипт Python, который создает демонстрационный каталог и проверяет запрос. Им не нужна облачная учетная запись, и они запускаются набором тестов проекта.
