# Распространенные ошибки StackQL

Большинство сбоев StackQL относятся к пяти категориям: отсутствующие провайдеры, неуказанные обязательные параметры, проблемы с аутентификацией, ограничения на стороне провайдера и контролируемые операции. Для каждой из них есть быстрый способ диагностики.

## Провайдер или таблица не найдены {#provider-or-table-not-found}

**Симптом**: запрос ссылается на `aws.ec2.instances` (или любой другой ресурс), но провайдер или таблицу не удается найти.

**Причина**: определения провайдеров не входят в поставку; они загружаются из реестра на каждую машину отдельно.

**Решение**:

```sql
SHOW PROVIDERS;          -- what is installed
REGISTRY LIST;           -- what is available
REGISTRY PULL aws;       -- install (repeat per provider)
```

Версии провайдеров также выводит `REGISTRY LIST` - повторная загрузка обновляет провайдер до последней опубликованной спецификации.

## Не указаны обязательные параметры {#missing-required-parameters}

**Симптом**: синтаксически правильная инструкция `SELECT` завершается ошибкой или ничего не возвращает, потому что не был указан обязательный параметр (обычно `region`, `subscriptionId`, `project`, `org` или идентификатор родительского ресурса).

**Причина**: у базовой операции API есть обязательные параметры маршрутизации; StackQL представляет их как обязательные предикаты `WHERE`.

**Решение**: выясните требования, а затем укажите параметры как предикаты равенства (или `IN`):

```sql
SHOW METHODS IN aws.ec2.instances;
```

Столбец `RequiredParams` показывает для каждого метода доступа, что именно должно содержать предложение `WHERE`, - для ресурса `aws.ec2.instances` метод `describe_instances` требует параметр `region`. Этот шаг обнаружения - задокументированная практика и для людей, и для агентов (MCP-сервер публикует те же данные через `list_methods`).

## Сбои аутентификации {#authentication-failures}

**Симптом**: команды метаданных (`SHOW`, `DESCRIBE`) работают, но инструкции `SELECT` или изменения данных завершаются ошибками 401/403 от провайдера.

**Причина**: метаданные берутся из локальных спецификаций провайдеров и не требуют учетных данных; операции с данными обращаются к провайдеру. Учетные данные отсутствуют в среде процесса, названы неправильно или недостаточны.

**Решение**: убедитесь, что переменные экспортированы в среде, из которой был запущен StackQL (процесс сервера или MCP наследует среду запуска - частая ошибка в том, что его не перезапускают после установки переменных), что имена соответствуют соглашению провайдера (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, `AZURE_TENANT_ID`/`AZURE_CLIENT_ID`/`AZURE_CLIENT_SECRET`, `GOOGLE_CREDENTIALS`, `STACKQL_GITHUB_USERNAME`/`STACKQL_GITHUB_PASSWORD`) и что у субъекта есть разрешения, необходимые для операции. Соглашения для каждого провайдера описаны в практических руководствах в разделе [/ai/how-tos](/ai/how-tos).

## Ограничение частоты запросов GitHub {#github-rate-limiting}

**Симптом**: запросы к GitHub без аутентификации какое-то время работают, а затем начинают завершаться ошибкой.

**Причина**: для доступа без аутентификации GitHub устанавливает лимит в 60 запросов к API в час с одного IP-адреса, а один запрос StackQL может выполнять несколько вызовов API с разбиением на страницы.

**Решение**: выполните аутентификацию с помощью персонального токена доступа (даже токен без областей существенно повышает лимит) - см. [Как настроить аутентификацию StackQL в GitHub](/ai/how-tos/authenticate-stackql-to-github).

## Пустые результаты там, где их быть не должно {#empty-results-that-should-not-be-empty}

**Симптом**: запрос выполняется успешно, но не возвращает ни одной строки для ресурсов, которые точно существуют.

**Что проверить**: предикаты маршрутизации указывают на правильную область (верный регион, проект, подписку или организацию); метод доступа, выбранный вашими предикатами, - тот, который вы имели в виду (`SHOW METHODS` показывает, какие комбинации предикатов выбирают какой метод, - например, `org =` или `username =` для ресурса `github.repos.repos`); и учетные данные позволяют видеть эти ресурсы (облачный IAM может незаметно отфильтровывать результаты списков).

## MCP-сервер отклонил изменение данных {#mcp-mutation-refused}

**Симптом**: инструкция `INSERT`/`UPDATE`/`DELETE`, которую агент выполняет через MCP-сервер, отклоняется с упоминанием elicitation или режима сервера.

**Причина**: это срабатывает контракт безопасности, а не ошибка. Режим `safe` по умолчанию требует подтверждения изменений данных человеком; клиенты, которые не объявляют возможность elicitation протокола MCP, не могут его предоставить.

**Решение**: используйте MCP-клиент с поддержкой elicitation (Claude Desktop, Cursor, Continue) и подтвердите запрос либо - только для доверенной неинтерактивной автоматизации - запустите сервер с `"mode": "full_access"`. Подробнее см. [Архитектура MCP-сервера StackQL](/ai/architecture/stackql-mcp-architecture).
