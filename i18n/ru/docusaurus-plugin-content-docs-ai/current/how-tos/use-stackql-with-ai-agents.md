Режим read_only сразу отклоняет изменения данных; delete_safe разрешает создание и обновление, но требует подтверждения для удаления; full_access разрешает любые операции. # Как использовать StackQL с ИИ-агентами

StackQL поставляется со встроенным сервером Model Context Protocol (MCP). Любой агент с поддержкой MCP - Claude, Cursor, Continue или собственный фреймворк агентов - подключается к нему и получает самоописываемый, управляемый SQL-интерфейс к каждому провайдеру облачных и SaaS-сервисов в реестре StackQL.

## Шаги {#steps}

1. **Задайте учетные данные провайдеров** в переменных среды перед запуском сервера (сервер наследует их):

```bash
export AWS_ACCESS_KEY_ID=YOURACCESSKEYID
export AWS_SECRET_ACCESS_KEY=YOURSECRETACCESSKEY
```

Либо (в выпусках StackQL после v0.10.542) укажите файл учетных данных в стиле dotenv с помощью флага `--env.file`; MCP-инструмент `reload_credentials` повторно загружает его посреди сеанса, поэтому смененные учетные данные попадают в работающий сервер без перезапуска.

2. **Запустите MCP-сервер.** Для автономного HTTP-сервера:

```bash
stackql mcp \
  --mcp.server.type=http \
  --mcp.config '{"server": {"transport": "http", "address": "127.0.0.1:9912", "allow_unauthenticated": true}}'
```

Начиная с выпуска `v0.12.742` транспорту HTTP требуется либо `server.auth_token_env_var` (переменная среды с заранее согласованным токеном bearer, который должен содержать каждый HTTP-запрос), либо явное включение `allow_unauthenticated`, как показано здесь, иначе сервер не запускается; используйте токен для любого прослушивателя, к которому могут обратиться другие процессы или хосты.  На `stdio` это не влияет.

Для клиентов, встроенных в редакторы, используйте флаг `--mcp.server.type=stdio` и позвольте клиенту самому запускать процесс (см. [Как использовать StackQL с Claude](/ai/how-tos/use-stackql-with-claude)). Чтобы обслуживать MCP и сетевой протокол PostgreSQL из одного процесса, используйте команду `stackql srv` с теми же MCP-флагами и флагом `--pgsrv.port`.

3. **Выберите режим безопасности.** Режим задается в конфигурации сервера и контролирует, что могут делать агенты:

| Режим | SELECT / метаданные | INSERT / UPDATE / REPLACE | DELETE | EXEC |
|---|---|---|---|---|
| `read_only` | разрешено | отклонено | отклонено | отклонено |
| `safe` (по умолчанию) | разрешено | требуется подтверждение | требуется подтверждение | требуется подтверждение |
| `delete_safe` | разрешено | разрешено | требуется подтверждение | требуется подтверждение |
| `full_access` | разрешено | разрешено | разрешено | разрешено |

"Требуется подтверждение" работает через MCP elicitation: клиент показывает пользователю ожидающий выполнения SQL, и пользователь принимает или отклоняет его. Закрепите `read_only` для агентов инвентаризации; оставьте `full_access` для доверенных конвейеров с проверяемым журналом аудита.  Полезная нагрузка из нескольких инструкций контролируется по самой привилегированной из них (начиная с выпуска `v0.12.742`), поэтому изменение данных не может пройти вслед за начальной инструкцией `SELECT`.

4. **Позвольте агенту сначала изучить схему, а затем выполнять запросы.** Типичный сеанс агента: `list_providers` -> `list_methods` (показывает обязательные параметры `WHERE`) -> `validate_select_query` -> `run_select_query`:

```sql
SELECT name, language, stargazers_count
FROM github.repos.repos
WHERE org = 'stackql';
```

Агент никогда не загружает SDK; схема определяется во время выполнения, а запрос - это обычный SQL.

## Аудит {#auditing}

Каждый вызов инструмента записывает одну запись JSONL - метка времени, инструмент, режим, решение, класс запроса, SQL, длительность - в файловое место назначения с ротацией журналов. Аудит включен по умолчанию и фиксирует, что сделал агент (а не строки результатов). В режиме обработки сбоев `strict`, используемом по умолчанию, сбой записи аудита возвращается как ошибка, а не позволяет изменению данных пройти без аудита.
