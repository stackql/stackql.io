# Почему файлы состояния не подходят для ИИ-агентов

Файлы состояния проектировались в расчете на допущения, которые ИИ-агенты нарушают: один автор изменений в каждый момент времени, изменения, собранные в редкие применения (apply) с проверкой людьми, и рабочий процесс, в котором допустимо, что состояние между обновлениями неактуально. Агенты работают параллельно, действуют непрерывно и рассуждают на основе тех фактов, которые им даны, - если эти факты берутся из файла состояния, агент рассуждает на основе неактуальной и неполной копии реальности.

## Допущения в явном виде {#the-assumptions-made-explicit}

Модель файла состояния работает, если:

1. **Операции записи выполняются последовательно.** Блокировка состояния предполагает, что конкуренция за нее возникает редко. Команды людей выполняют apply несколько раз в день; конкуренция за блокировку - граничный случай.
2. **Чтение происходит на этапе планирования.** Состояние обновляется, когда человек запускает plan; неактуальность в промежутках незаметна, потому что никто на него не смотрит.
3. **Управляемое множество совпадает со значимым.** Файл состояния описывает только ресурсы, созданные инструментом. Рабочий процесс исходит из того, что за его пределами нет ничего важного.
4. **Ошибки исправляют эксперты.** Поврежденное или разошедшееся с реальностью состояние исправляет специалист, вручную правящий состояние (импорт, перемещение, ручные правки).

При агентной работе каждое из этих допущений нарушается. Агенты действуют за секунды, поэтому последовательные операции записи становятся пределом пропускной способности, а конкуренция за блокировку - нормой. Агенты наблюдают непрерывно, поэтому неактуальность между обновлениями превращается в поток ложных предпосылок. Агентов постоянно спрашивают обо всей среде ("открыто ли что-нибудь для публичного доступа?"), и важен именно ответ за пределами управляемого множества. А агент, повредивший состояние, не может надежно исправить его сам - цикл исправления рассчитывал на суждение человека.

## Более глубокая проблема: копия становится интерфейсом {#the-deeper-problem-the-copy-is-the-interface}

Эти проблемы сводятся к одному проектному решению: файл состояния делает *копию* состояния инфраструктуры рабочим интерфейсом системы. У любой копии есть проблема синхронизации, и ее наследует каждый потребитель копии. [Дрейф инфраструктуры](/ai/canonical-definitions/what-is-infrastructure-drift) - не эксплуатационная случайность, а закономерное поведение копии в среде, где реальность меняется по другим каналам - через консоли, автомасштабирование, другие инструменты и других агентов.

Рабочие процессы людей компенсируют это регламентами: заморозкой изменений, требованием использовать единственный инструмент, периодическим согласованием. Агентные среды так не могут - ценность агентов в том, что они действуют часто и независимо, а именно такой характер нагрузки делает скоординированную копию неподдерживаемой.

## Базовый механизм на замену {#the-replacement-primitive}

Сама плоскость управления уже представляет собой согласованное, авторитетное и безопасное при параллельном доступе хранилище состояния - его обслуживают поставщики. Агентам нужен интерфейс к ней, соответствующий тому, как они работают: декларативные запросы к текущему состоянию, единообразные для всех провайдеров, с изменениями, выраженными в той же грамматике и контролируемыми политиками. Именно эту модель реализует StackQL:

```sql
SELECT instance_id, instance_type, launch_time
FROM aws.ec2.instances
WHERE region = 'us-east-1';
```

Результат верен на момент выполнения, включает неуправляемые ресурсы, не требует блокировки и не нуждается в процессе исправления - повреждать нечего. Сопоставление идентификаторов и упорядочение зависимостей (обоснованные задачи файла состояния) переходят в движок запросов и оркестрацию развертывания (stackql-deploy), а не в изменяемый артефакт, согласованность которого агент должен поддерживать.
