# Почему SQL хорошо подходит в качестве интерфейса к облачным API

SQL подходит для облачных API по четырем причинам: он декларативный (вызывающая сторона указывает, что нужно, а не как), ориентирован на множества (облачные среды - это множества ресурсов), поддерживается повсеместно (с ним работают любой драйвер, любая платформа BI и любой блокнот) и - решающая причина в эпоху агентов - это язык запросов, на котором уже свободно пишет любая ИИ-модель. Выбор SQL в качестве интерфейса к плоскости управления означает, что затраты на интеграцию со всем набором инструментов и экосистемой моделей уже оплачены.

## Структурное соответствие {#the-structural-fit}

Облачные ресурсы по своей природе реляционны. Каждый поставщик организует свою среду в виде типизированных коллекций (экземпляры, бакеты, репозитории) объектов с атрибутами, идентификаторами и перекрестными ссылками между ними. Это схема, и поставщики уже публикуют ее - в виде спецификаций OpenAPI. Операции над этими коллекциями имеют ровно те формы, для которых в SQL есть названия: перечисление и фильтрация (`SELECT ... WHERE`), создание (`INSERT`), изменение (`UPDATE`), удаление (`DELETE`). Сопоставление, которое применяет StackQL, механическое, а не метафорическое - именно поэтому его можно генерировать из спецификаций для сотен сервисов. См. [Что такое SQL для API?](/ai/canonical-definitions/what-is-sql-for-apis).

Ориентация на множества важнее, чем кажется на первый взгляд. Вопросы об инфраструктуре - это вопросы о множествах: "все экземпляры без этого тега", "бакеты, сгруппированные по регионам", "репозитории, в которых отключена защита веток". Императивный код на SDK отвечает на них циклами, обработкой разбиения на страницы и накоплением результатов. В SQL это одно выражение:

```sql
SELECT region, COUNT(*) as num_functions
FROM aws.lambda.functions
WHERE region IN ('us-east-1','us-west-2','eu-west-1')
GROUP BY region;
```

StackQL выполняет этот запрос как параллельные вызовы API по регионам; вызывающей стороне не пришлось писать fan-out.

## Аргумент для эпохи агентов {#the-agent-era-argument}

Для ИИ-агентов выбор интерфейса - это решение об экономике токенов и надежности:

- **Компетентность без примеров (zero-shot).** SQL - одна из самых плотно представленных компетенций в обучающих данных любой модели. Агент пишет правильный запрос с фильтрацией, агрегацией и соединениями без обучения в контексте. Собственный DSL или отдельный SDK для каждого поставщика приходится объяснять в промпте, снова и снова, расплачиваясь токенами и ошибками.
- **Небольшая замкнутая грамматика для огромного набора операций.** Поставщики облачных услуг предоставляют десятки тысяч операций. Если опубликовать их как отдельные инструменты или функции, выбор инструмента становится непосильной задачей. Если выразить их как SQL поверх обнаруживаемых схем, грамматика остается неизменной, а инструкции `SHOW PROVIDERS`, `SHOW METHODS` и `DESCRIBE` позволяют агенту изучать доступные операции во время выполнения - и платить за то, что ему нужно, тогда, когда это нужно.
- **Проверяемость.** Декларативную форму SQL можно проверить до выполнения. Человек (или политика контроля, например режим safe MCP-сервера StackQL) может прочитать инструкцию и точно знать, что она затронет, - со скриптом из императивных вызовов SDK это гораздо сложнее.

## Что SQL дает помимо агентов {#what-sql-buys-beyond-agents}

Тот же выбор связывает инфраструктуру с аналитическим стеком: в режиме сервера StackQL использует сетевой протокол PostgreSQL, поэтому psql, DBeaver, Tableau, Power BI, Superset, pandas и Jupyter обращаются к актуальному состоянию облака так, как если бы это была база данных. Панели инвентаризации, отчеты по безопасности и анализ FinOps используют имеющиеся навыки и инструменты без промежуточного экспортера или конвейера ETL.
