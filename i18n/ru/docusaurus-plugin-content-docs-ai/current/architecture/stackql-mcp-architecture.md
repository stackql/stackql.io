# Архитектура MCP-сервера StackQL

MCP-сервер StackQL встроен в двоичный файл движка и публикует возможности StackQL (обнаружение, описание, проверку, выполнение) в виде инструментов Model Context Protocol. Его архитектура строится на трех принципах: небольшой универсальный набор инструментов вместо отдельного инструмента для каждой операции, многоуровневый контракт безопасности для изменения данных и журнал аудита, который фиксирует все действия агента.

## Транспорты и режимы развертывания {#transports-and-deployment-modes}

| Режим | Команда | Использование |
|---|---|---|
| stdio | `stackql mcp --mcp.server.type=stdio` | Клиенты, встроенные в редакторы (Claude Desktop, Cursor, Continue), которые запускают процесс напрямую |
| HTTP (автономный) | `stackql mcp --mcp.server.type=http` | Долго работающий сервер для автономных агентов |
| Два сервера, обмен в памяти | `stackql srv --mcp.server.type=http --pgsrv.port <port>` | MCP и сетевой протокол PostgreSQL в одном процессе |
| Обратный прокси | `stackql srv --mcp.server.type=reverse_proxy` | MCP-запросы передаются базовому серверу StackQL Postgres через DSN; поддерживает разделение рабочих нагрузок и TLS |

Конфигурация - это JSON-объект (или YAML-объект), который передается через флаг `--mcp.config` и охватывает транспорт, адрес, пути к сертификатам TLS, аутентификацию клиентов, режим, настройки аудита и необязательные списки разрешенных `enabled_tools` / `enabled_prompts` для публикации суженного набора возможностей (например, сервер инвентаризации только для чтения, который предоставляет только `server_info` и `list_providers`). Начиная с `v0.12.742` транспорт HTTP требует либо заранее согласованный токен bearer (`server.auth_token_env_var`), либо явное включение `server.allow_unauthenticated`; запросы между источниками из браузера отклоняются.

## Набор инструментов {#the-tool-surface}

Пятнадцать инструментов, каждый из которых возвращает текстовое отображение для LLM и типизированную структурированную полезную нагрузку:

- **Обнаружение**: `list_providers`, `list_services`, `list_resources`, `list_methods`, `describe_method` - обход иерархии, который выявляет обязательные параметры `WHERE` еще до написания запроса.
- **Реестр**: `list_registry` (доступные провайдеры и версии), `pull_provider` (установка в локальный кэш).
- **Проверка**: `validate_select_query` - синтаксический анализ и планирование инструкции `SELECT` без выполнения.
- **Query Library**: `query_library_search` (поиск отобранных шаблонов запросов по намерению, провайдеру, сервису и тегам), `query_library_get` (проверка параметров и возврат сформированного SQL без его выполнения).
- **Выполнение**: `run_select_query` (чтение), `run_mutation_query` (`INSERT`/`UPDATE`/`REPLACE`/`DELETE` - реальные побочные эффекты), `run_lifecycle_operation` (`EXEC`).
- **Идентификационные сведения**: `server_info` - версия, бэкенд, реестр, режим; вызывается по требованию (чтобы диагностировать отклоненную или контролируемую операцию либо проверить поведение, зависящее от версии), а не в начале сеанса.
- **Учетные данные**: `reload_credentials` - повторно загружает файл dotenv `--env.file` в среду процесса посреди сеанса и сообщает статус определения учетных данных для каждого провайдера; только имена и статусы, никогда значения секретов (доступно в выпусках после v0.10.542).

Публикуются семь промптов: `getting_started` (ознакомительный обзор для новых пользователей), `cloud_audit`, `cost_cleanup`, `drift_report`, `iam_access_review`, `public_exposure_scan` и `create_deploy_stack`; каждый из них - это пошаговый рабочий процесс, который агент выполняет с помощью перечисленных выше инструментов, не изменяя облачные ресурсы.

## Контракт безопасности {#the-safety-contract}

Параметр `server.mode` выбирает один из четырех контрактов; все они разрешают `SELECT` и операции с метаданными и различаются в отношении операций записи:

| Режим | INSERT / UPDATE / REPLACE | DELETE | EXEC |
|---|---|---|---|
| `read_only` | отклонено | отклонено | отклонено |
| `safe` (по умолчанию) | требуется подтверждение | требуется подтверждение | требуется подтверждение |
| `delete_safe` | разрешено | требуется подтверждение | требуется подтверждение |
| `full_access` | разрешено | разрешено | разрешено |

"Требуется подтверждение" реализовано с помощью MCP elicitation: сервер отправляет клиенту ожидающее действие (инструмент, класс запроса, SQL), и человек принимает или отклоняет его. Клиенты, которые не объявляют поддержку elicitation, получают отказ, который указывает оператору на режим `full_access`; таким образом, изменение данных без участия человека требует явного включения и не происходит по умолчанию. Режим задается глобально для всего сервера; переопределений для отдельных инструментов нет. Полезная нагрузка, содержащая несколько инструкций, контролируется по самой привилегированной из них (начиная с `v0.12.742`), а `validate_select_query` принимает ровно одну инструкцию.

## Подсистема аудита {#the-audit-subsystem}

Каждый вызов инструмента записывает одну запись JSONL - метка времени, инструмент, режим, решение (`allow`, `refuse_immediate`, `needs_approval_accepted` и так далее), класс запроса, SQL, аргументы, длительность, ошибка - в файловое место назначения с ротацией по размеру, возрасту и количеству резервных копий. Журнал отвечает на вопрос "что сделал агент" и намеренно не отвечает на вопрос "что увидел агент": строки результатов `SELECT` исключаются как потенциально большие и конфиденциальные. Запись в журнал происходит после выполнения, но до возврата ответа; в режиме обработки сбоев `strict`, который действует по умолчанию, сбой аудита при успешном изменении данных возвращает клиенту ошибку - это намеренное решение, чтобы ни одна инструкция `DELETE` не завершилась без аудита.
