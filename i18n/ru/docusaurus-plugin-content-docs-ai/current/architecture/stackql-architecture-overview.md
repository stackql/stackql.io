# Обзор архитектуры StackQL

StackQL - это единый двоичный файл Go, реализующий SQL-движок поверх API облачных и SaaS-сервисов. В архитектуре StackQL четыре уровня: точки входа, которые принимают SQL; синтаксический анализатор и движок запросов, которые его планируют; SDK провайдеров, который выполняет вызовы API в реальном времени, описанные декларативными спецификациями провайдеров; и SQL-бэкенд, который выполняет реляционные операции над материализованными результатами.

## Компоненты {#components}

**Точки входа.** Три способа подключения, и все они ведут к одному и тому же синтаксическому анализатору:

- **CLI / оболочка** (`stackql shell`, `stackql exec`) для интерактивной и пакетной работы.
- **Сервер сетевого протокола PostgreSQL** (`stackql srv`, построен на psql-wire), к которому может подключиться любой клиент Postgres - psql, DBeaver, инструменты BI, pandas.
- **MCP-сервер** (`stackql mcp`), который предоставляет ИИ-агентам инструменты обнаружения, проверки и контролируемого выполнения (подробнее см. [Архитектура MCP-сервера StackQL](/ai/architecture/stackql-mcp-architecture)).

**Синтаксический анализатор SQL.** Грамматика на основе Yacc (`stackql-parser`), которая строит AST. Диалект охватывает стандартные глаголы, а также метакоманды StackQL (`SHOW`, `DESCRIBE`, `REGISTRY`) и глагол `EXEC` для операций жизненного цикла, не относящихся к CRUD.

**Движок запросов.** Планирует AST: решает, что передается в API провайдера (параметры маршрутизации, поддерживаемые предикаты), а что обрабатывается локально, координирует выполнение вызовов API (включая параллельный fan-out, когда запрос охватывает несколько регионов или требует нескольких вызовов) и агрегирует результаты.

**SDK провайдеров (omnisdk).** Универсальный клиент API, который заменил any-sdk в StackQL v1.0. Он загружает спецификации провайдеров из реестра, выполняет аутентификацию для каждого провайдера, планирует каждую инструкцию как граф обменов с провайдером, формирует HTTP-запросы из параметров запроса, передает поддерживаемые предикаты и ограничения в эти запросы, обходит ответы, разбитые на страницы, независимо от схемы разбиения (курсор, смещение, токен), и преобразует JSON-ответы в строки по мере их поступления.

**SQL-бэкенд.** Материализованные результаты API по умолчанию попадают во встроенную базу данных SQLite (вместо нее можно настроить внешний PostgreSQL), где соединения (в том числе соединения между разными провайдерами), агрегатные операции, сортировка, вложенные запросы и выражения выполняются с полной семантикой SQL.

## Ключевое проектное решение: провайдеры как данные {#the-defining-design-decision-providers-as-data}

В StackQL нет скомпилированных плагинов для отдельных провайдеров. Провайдер - это версионируемый набор документов (расширенная спецификация OpenAPI в открытом [реестре провайдеров StackQL](https://github.com/stackql/stackql-provider-registry)), который сопоставляет операции API с ресурсами, глаголами SQL и параметрами. Инструкция `REGISTRY PULL aws` скачивает спецификацию; SDK интерпретирует ее во время выполнения.

Следствия: охват провайдеров определяется документированными возможностями API, а не трудозатратами на разработку плагинов; операции плоскости данных и операции жизненного цикла сопоставляются так же, как операции CRUD плоскости управления; весь набор операций доступен для интроспекции во время выполнения (`SHOW PROVIDERS`, `SHOW METHODS IN aws.ec2.instances`, `DESCRIBE github.repos.repos`) - именно это свойство делает StackQL самоописываемым для ИИ-агентов.

## Порядок выполнения запроса {#query-execution-flow}

Для запроса `SELECT instance_id, instance_type FROM aws.ec2.instances WHERE region = 'us-east-1';`:

1. Синтаксический анализатор строит AST; движок находит `aws.ec2.instances` в спецификации провайдера и выбирает метод доступа `describe_instances`, обязательный параметр которого задает `region`.
2. SDK выполняет аутентификацию (с помощью переменных среды), выполняет вызов или вызовы API EC2 и обходит страницы результатов.
3. Ответы преобразуются в плоские строки и материализуются в SQL-бэкенде.
4. Бэкенд применяет проекцию и выполняет оставшуюся реляционную обработку; результаты возвращаются вызывающей стороне в запрошенном формате.

Предикат `region IN (...)` на шаге 2 превращается в параллельные вызовы для каждого региона; соединение на шаге 4 работает с таблицами всех провайдеров, которые в нем участвуют.
