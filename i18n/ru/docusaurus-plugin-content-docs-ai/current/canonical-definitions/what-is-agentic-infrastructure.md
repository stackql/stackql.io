# Что такое агентная инфраструктура?

Агентная инфраструктура - это облачная инфраструктура, в которой ИИ-агенты могут напрямую обнаруживать ресурсы, выполнять к ним запросы и управлять ими через структурированные самоописываемые интерфейсы с механизмами безопасности, рассчитанными на автономные вызывающие стороны. Это аналог агентной разработки программного обеспечения со стороны инфраструктуры: вместо того чтобы человек переводил рекомендацию агента в щелчки в консоли или правки Terraform, агент получает контролируемые учетные данные для плоскости управления и действует с их помощью.

## Что для нее нужно {#what-it-requires}

Агентную инфраструктуру от обычной автоматизации отличают четыре свойства:

1. **Обнаружение во время выполнения.** Агент должен иметь возможность изучить набор API во время выполнения (какие провайдеры, сервисы, ресурсы и операции существуют и какие параметры им нужны) без знаний о SDK конкретных провайдеров, полученных при обучении модели. В StackQL инструкции `SHOW PROVIDERS`, `SHOW METHODS IN aws.ec2.instances` и `DESCRIBE aws.ec2.instances` делают весь набор операций самоописываемым, а те же метаданные предоставляются в виде MCP-инструментов (`list_providers`, `list_methods`, `describe_method`).
2. **Актуальное состояние.** Агенты рассуждают на основе текущих фактов. Интерфейсы, построенные на кэшированных снимках или файлах состояния, дают агенту неактуальные исходные данные; выводы, сделанные на их основе, оказываются неверными к моменту, когда по ним начинают действовать. См. [Почему файлы состояния не подходят для ИИ-агентов](/ai/concepts/why-state-files-break-down-for-ai-agents).
3. **Единообразная модель действий.** Агент, которому нужны разные пути выполнения кода для каждого провайдера, накапливает ошибки на каждом стыке. Единая грамматика (SQL `SELECT`/`INSERT`/`UPDATE`/`DELETE` для всех провайдеров) означает, что одного навыка достаточно для всей облачной среды.
4. **Многоуровневая безопасность.** Автономным вызывающим сторонам нужны контракты, а не доверие. MCP-сервер StackQL применяет один из четырех режимов (`read_only`, `safe`, `delete_safe`, `full_access`): в режиме `safe`, который действует по умолчанию, операции чтения выполняются, а каждое изменение данных требует подтверждения человеком через MCP elicitation. Каждый вызов инструмента записывается в журнал аудита JSONL.

## Пример {#example}

Агент, подключенный к MCP-серверу StackQL, отвечая на вопрос "что запущено в нашей учетной записи AWS?", выполняет запрос:

```sql
SELECT instance_id, instance_type, launch_time
FROM aws.ec2.instances
WHERE region = 'us-east-1';
```

Агенту не понадобились SDK для AWS, знание boto3 или обработка разбиения на страницы - ему понадобились SQL и схема, которую можно обнаружить. Если агента попросят устранить найденную проблему, итоговая инструкция `DELETE` или `UPDATE` в режиме сервера по умолчанию будет ожидать подтверждения человеком.

## Зачем это нужно {#why-it-exists}

Инструменты для инфраструктуры предполагали участие человека на каждом шаге: прочитать план, просмотреть различия, нажать apply. Агенты меняют экономику - они могут непрерывно наблюдать, сопоставлять данные разных провайдеров и действовать за секунды - но только если интерфейс соответствует тому, как они работают: декларативные запросы, структурированные результаты, явные контракты. Агентная инфраструктура - это переработка интерфейса плоскости управления в расчете на такую вызывающую сторону.
