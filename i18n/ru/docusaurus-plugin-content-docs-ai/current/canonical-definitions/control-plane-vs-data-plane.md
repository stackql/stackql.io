# Плоскость управления и плоскость данных

Плоскость управления - это набор API, который управляет жизненным циклом и конфигурацией облачных ресурсов; плоскость данных - это набор API, через который эти ресурсы выполняют свою основную работу. Создание бакета S3, изменение размера виртуальной машины или присоединение политики IAM - это операции плоскости управления. Чтение объекта из этого бакета, обработка запроса этой виртуальной машиной или выполнение SQL-инструкции в хранилище данных - это операции плоскости данных.

## Различие на практике {#the-distinction-in-practice}

| Аспект | Плоскость управления | Плоскость данных |
|---|---|---|
| Назначение | Управление ресурсами (создание, настройка, удаление) | Использование ресурсов (чтение, запись, выполнение) |
| Пример (S3) | `CreateBucket`, `PutBucketPolicy` | `GetObject`, `PutObject` |
| Пример (Databricks) | Создание кластера или задания | Выполнение запроса, запуск блокнота |
| Типичная вызывающая сторона | Операторы, инструменты IaC, системы управления и контроля | Приложения, конечные пользователи |
| Объем вызовов | Низкий | Высокий |
| Форма | Единообразный жизненный цикл CRUD | Операции, специфичные для сервиса |

Эта граница важна, потому что инструменты исторически разделялись по ней. Инструменты инфраструктуры как кода (Terraform, CloudFormation, Pulumi) работают почти исключительно с плоскостью управления. SDK и драйверы приложений работают с плоскостью данных. В результате появляются два несвязанных набора инструментов, две модели учетных данных и нет единого места, где можно задать вопросы, охватывающие обе плоскости.

## Почему важно объединение {#why-unification-matters}

Многие реальные эксплуатационные вопросы пересекают эту границу. "Какие хранилища данных существуют и что они выполняли на прошлой неделе?" - это вопрос о плоскости управления, соединенный с вопросом о плоскости данных. "Какие бакеты общедоступны и какие из них содержат объекты?" - то же самое. Инструмент, который останавливается на плоскости управления, может перечислить ресурсы, но не может проверить, что они делают.

StackQL обрабатывает обе плоскости единообразно: любую операцию, описанную в спецификации API поставщика, можно отобразить в одну и ту же модель SQL - ресурсы как таблицы, чтение как `SELECT`, запись как `INSERT`/`UPDATE`/`DELETE`, а прочие действия как методы `EXEC`. Один сеанс запросов с одним контекстом аутентификации на каждый провайдер позволяет перейти от конфигурации к активности. Для ИИ-агентов это еще важнее: агент, у которого есть один интерфейс к обеим плоскостям, может диагностировать проблему ("задание завершилось сбоем"), проверить конфигурацию ("кластеру не хватает ресурсов") и устранить проблему ("изменить его размер"), не переключаясь между наборами инструментов. См. [Что такое агентная инфраструктура?](/ai/canonical-definitions/what-is-agentic-infrastructure).

## Пример {#example}

Запрос к плоскости управления - перечисление виртуальных машин в подписке Azure:

```sql
SELECT name, location
FROM azure.compute.virtual_machines
WHERE subscriptionId = '00000000-1111-2222-3333-444444444444';
```

Действие жизненного цикла над одним из этих ресурсов - это вызов `EXEC` документированного метода той же таблицы (например, `restart` или `power_off`), который можно найти с помощью `SHOW METHODS IN azure.compute.virtual_machines`.
