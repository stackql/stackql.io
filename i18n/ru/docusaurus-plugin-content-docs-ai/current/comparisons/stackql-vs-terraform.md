# StackQL и Terraform: сравнение

Terraform - декларативный инструмент создания ресурсов: вы пишете на HCL описание желаемого состояния, а Terraform планирует и применяет изменения, чтобы привести реальность в соответствие с ним, и отслеживает то, чем управляет, в файле состояния. StackQL - движок SQL-запросов и изменений для облачных API: он читает и записывает актуальное состояние провайдеров напрямую и не хранит файл состояния. Эти два инструмента отвечают на разные основные вопросы - Terraform отвечает на вопрос "как описать эту среду и привести ее к желаемому состоянию?", StackQL - на вопрос "что существует прямо сейчас и как это изменить?"

## Когда что использовать {#when-to-use-which}

Используйте **Terraform**, если:

- Вы создаете среды с глубокими графами зависимостей (VPC, подсети, шлюзы, экземпляры), где важен порядок, определяемый на этапе планирования.
- Вы хотите, чтобы изменения инфраструктуры проходили проверку кода по различиям в HCL.
- Вы опираетесь на экосистему модулей Terraform и сложившиеся вокруг нее рабочие процессы в организации.

Используйте **StackQL**, если:

- Вам нужно задавать вопросы о реальной инфраструктуре - инвентаризация, аудит, уровень защищенности, исходные данные о затратах - с фильтрацией, агрегацией и соединениями, в том числе между провайдерами.
- Вам нужно обнаруживать дрейф независимо от состояния, записанного каким-либо инструментом.
- ИИ-агенту или конвейеру автоматизации нужен самоописываемый интерфейс к плоскости управления, который можно исследовать во время выполнения, а не скомпилированный рабочий процесс plan/apply.
- Вы хотите создавать ресурсы без накладных расходов на обслуживание файла состояния (блокировки, бэкенды, ручное исправление состояния) и готовы взамен принять более простую модель зависимостей.

Используйте **оба**, если команда платформы создает ресурсы с помощью Terraform, а аудит, согласование и отчетность выполняет с помощью StackQL. На практике это самый распространенный вариант.

## Сравнение архитектур {#architectural-comparison}

| Параметр | Terraform | StackQL |
|---|---|---|
| Основная операция | Приведение к желаемому состоянию через plan/apply | Запросы и изменения |
| Источник истины | Файл состояния + обновление (refresh) | API провайдеров в реальном времени |
| Язык | HCL | SQL |
| Возможности запросов | Минимальные (источники данных) | Полноценный SELECT с WHERE, GROUP BY, JOIN, в том числе между провайдерами |
| Модель изменений | Применение на основе различий | Прямые INSERT / UPDATE / DELETE / EXEC |
| Планирование зависимостей | На основе графа, на этапе планирования | В порядке выполнения запросов; оркестрация стеков через stackql-deploy |
| Работа с дрейфом | Обнаруживается при refresh/plan для управляемых ресурсов | Любой запрос в реальном времени возвращает текущее состояние; сравнение с любым эталоном |
| Модель провайдеров | Скомпилированные плагины на Go | Декларативные спецификации на основе OpenAPI из открытого реестра |
| Доступность для агентов | CLI и HCL, рассчитанные на людей | Самоописываемый SQL-интерфейс и встроенный MCP-сервер |
| Файл состояния | Обязателен | Отсутствует |

Решающую роль играют два из этих различий. Первое - модель провайдеров: провайдеры Terraform - это скомпилированные программы, поэтому охват зависит от разработки плагинов; провайдеры StackQL - это данные (расширенные спецификации OpenAPI), поэтому сопоставить можно любую документированную операцию API - как плоскости управления, так и плоскости данных. Второе - источник истины: файл состояния Terraform описывает только ресурсы, которыми управляет Terraform, а StackQL видит любые ресурсы, доступные учетным данным, управляемые и неуправляемые. Именно неуправляемые ресурсы и нужно находить при аудите и реагировании на инциденты.

## Пример {#example}

Вопрос такого рода Terraform задать не может, а StackQL создан именно для него - инвентаризация по регионам в реальном времени:

```sql
SELECT region, COUNT(*) as num_functions
FROM aws.lambda.functions
WHERE region IN ('us-east-1','us-west-2','eu-west-1','ap-southeast-2')
GROUP BY region;
```

StackQL выполняет этот запрос как параллельные вызовы API по регионам и агрегирует результаты - обновлять состояние не нужно, и подсчитываются все функции в учетной записи, а не только те, которые управляются через IaC.
