  - question: StackQL - это MCP-сервер?
    answer: Да. StackQL поставляется со встроенным MCP-сервером (stackql mcp или stackql srv, чтобы запустить его вместе с сервером сетевого протокола PostgreSQL). Он предоставляет обнаружение провайдеров, описание схем, проверку запросов и контролируемое выполнение запросов в виде MCP-инструментов через транспорты stdio или HTTP.

    answer: Из-за масштаба. Доступны также режимы read_only, delete_safe и full_access, а каждый вызов инструмента записывается в журнал аудита в формате JSONL.

# StackQL и собственные MCP-серверы: сравнение

Собственный MCP-сервер представляет конкретный API или рабочий процесс в виде написанных вручную инструментов для ИИ-агентов; встроенный MCP-сервер StackQL предоставляет все возможности каждого поддерживаемого провайдера облачных платформ и SaaS-сервисов через небольшой набор универсальных самоописываемых инструментов плюс SQL. Сравниваются два подхода: подбор инструментов для каждой предметной области и одна абстракция, доступная агенту для запросов, над всеми предметными областями.

## Когда что использовать {#when-to-use-which}

Создавайте **собственный MCP-сервер**, если:

- Предметная область узкая, а операций немного - дюжина инструментов с понятными именами и строгими схемами может превзойти универсальный интерфейс по надежности в этом конкретном рабочем процессе.
- Между агентом и API нужна объемная бизнес-логика: подтверждения, обогащение данных, многошаговые транзакции, которые агент должен видеть как один атомарный инструмент.
- Целевой API внутренний или проприетарный и не описан публичной спецификацией.

Используйте **MCP-сервер StackQL**, если:

- Предметная область - облачная и SaaS-инфраструктура (AWS, Azure, Google Cloud, GitHub, Databricks, Snowflake, Okta и остальные провайдеры из реестра провайдеров), где из-за количества операций отдельные инструменты для каждой операции непрактичны.
- Вы хотите, чтобы агент обнаруживал возможности во время выполнения (`list_providers` -> `list_services` -> `list_resources` -> `list_methods` -> `describe_method`), а не был ограничен инструментами, которые кто-то предусмотрел заранее.
- Вам нужны управляемые операции записи: контракт безопасности из четырех режимов (`read_only`, `safe`, `delete_safe`, `full_access`) с подтверждением человеком через elicitation и постоянно включенным журналом аудита вместо логики безопасности, которую вы пишете и поддерживаете сами.
- Вам нужна единая точка управления учетными данными и политиками для всей среды вместо отдельного специально написанного сервера для каждого провайдера.

Эти подходы можно сочетать: команды часто используют StackQL MCP для общего доступа к инфраструктуре вместе с небольшими собственными MCP-серверами для проприетарных внутренних систем.

## Экономика токенов {#the-token-economics}

Практическое ограничение для инструментов агентов - контекст. Определения инструментов занимают контекстное окно агента еще до начала какой-либо работы, а точность выбора инструментов снижается по мере роста их количества. Публикация одного только AWS в виде отдельных инструментов для каждой операции означала бы тысячи определений. Архитектура StackQL ограничивает опубликованный набор пятнадцатью инструментами (обнаружение, описание, проверка, выполнение, управление реестром, Query Library) и переносит выразительную мощь в SQL - язык, на котором любая современная модель уже свободно пишет. Затраты агента на задачу в токенах - это короткая SQL-строка, а не согласование схем инструментов. Этот аргумент развивается на странице [Почему SQL хорошо подходит в качестве интерфейса к облачным API](/ai/concepts/why-sql-is-a-strong-interface-for-cloud-apis).

## Пример {#example}

Сеанс агента с MCP-сервером StackQL после того, как обязательные параметры обнаружены с помощью инструмента `list_methods`:

```sql
SELECT name, visibility, default_branch
FROM github.repos.repos
WHERE org = 'stackql';
```

Тот же инструмент (`run_select_query`) обслуживает этот запрос и любое другое чтение у любого провайдера; запросы на изменение данных проходят через инструмент `run_mutation_query`, где режим сервера решает, будут ли они выполнены, потребуют подтверждения или будут отклонены.
