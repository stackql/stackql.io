# StackQL и Steampipe: сравнение

Steampipe и StackQL реализуют одну и ту же основную идею - API облачных платформ и SaaS-сервисов, представленные в виде SQL-таблиц, - с одним решающим отличием: Steampipe предназначен только для чтения, а StackQL также выполняет запись. Steampipe содержит встроенный PostgreSQL и отображает API через оболочки сторонних данных, которые получают данные от плагинов на Go; StackQL реализует собственный SQL-движок поверх декларативных спецификаций провайдеров, полученных из OpenAPI, и отображает полный набор глаголов: `SELECT`, `INSERT`, `UPDATE`, `REPLACE`, `DELETE` и `EXEC` для действий жизненного цикла.

## Когда что использовать {#when-to-use-which}

Используйте **Steampipe**, если:

- Ваш сценарий использования - исключительно чтение: инвентаризация, панели соответствия требованиям, уровень защищенности.
- Вам нужна его зрелая экосистема модов для проверки соответствия требованиям (CIS, SOC 2 и аналогичные готовые пакеты эталонных проверок).
- Вы уже вложились в инструменты на основе PostgreSQL FDW и в окружающую их экосистему Turbot.

Используйте **StackQL**, если:

- Вам нужны чтение и запись в одном инструменте - найти ошибку конфигурации запросом, а затем исправить ее инструкцией `UPDATE` в том же сеансе.
- Вы разрабатываете решения для ИИ-агентов: StackQL включает встроенный MCP-сервер с инструментами обнаружения, проверкой запросов, режимами контроля изменений и журналом аудита.
- Вам нужен охват провайдеров, основанный на спецификациях API, а не на разработке плагинов, включая операции плоскости данных и операции жизненного цикла.
- Вам нужен детерминированный единый двоичный файл с минимумом зависимостей, который в режиме сервера также поддерживает сетевой протокол PostgreSQL.

Оба инструмента имеют открытый исходный код, оба работают локально или в конвейерах, и для запросов инвентаризации только на чтение они действительно взаимозаменяемы по возможностям; в этом случае выбор сводится к предпочтениям в отношении схемы и экосистемы.

## Сравнение архитектур {#architectural-comparison}

| Критерий | Steampipe | StackQL |
|---|---|---|
| Глаголы SQL | Только SELECT | SELECT, INSERT, UPDATE, REPLACE, DELETE, EXEC |
| Движок | Встроенный PostgreSQL + оболочки сторонних данных | Собственный SQL-движок (встроенный SQLite или бэкенд PostgreSQL) |
| Определение провайдеров | Скомпилированные плагины на Go | Декларативные расширенные спецификации OpenAPI в открытом реестре |
| Охват плоскостей | Чтение в плоскости управления | Плоскость управления и плоскость данных, чтение и запись |
| Интерфейс для ИИ-агентов | Стандартное подключение к Postgres | Встроенный MCP-сервер с режимами безопасности и журналом аудита |
| Режим сервера | Сетевой протокол Postgres (steampipe service) | Сетевой протокол Postgres (stackql srv) плюс MCP (stackql mcp) |
| Материалы по соответствию требованиям | Обширная библиотека модов | На основе запросов; нет готовой библиотеки эталонных проверок |

Разница в определении провайдеров со временем накапливается: таблица Steampipe появляется, когда кто-то пишет для нее код плагина, а таблица StackQL появляется, когда операция API описана в спецификации провайдера. Разница в возможности записи принципиальная: замкнутые рабочие процессы - обнаружить, решить, исправить - укладываются в один сеанс StackQL, тогда как Steampipe передает исправление другому инструменту.

## Пример {#example}

Намерение в обоих инструментах одинаковое, но в StackQL последующее исправление выполняется на том же языке. Выполните запрос к экземплярам EC2:

```sql
SELECT instance_id, instance_type, launch_time
FROM aws.ec2.instances
WHERE region = 'us-east-1';
```

Затем исправление в StackQL выполняется инструкцией `DELETE` или `EXEC` (например, завершение или остановка экземпляра) для той же таблицы с учетом разрешений, предоставленных учетным данным, и - при работе в качестве MCP-сервера - настроенного режима безопасности.
