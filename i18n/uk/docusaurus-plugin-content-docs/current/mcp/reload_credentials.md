Повторно завантажує в середовище процесу сервера файл у форматі dotenv, вказаний прапорцем [`--env.file`](/command-line-usage/global-flags), а потім повідомляє стан визначення облікових даних для кожного провайдера.  Це розв'язує проблему середовища, зафіксованого під час запуску: облікові дані, які записали на диск або ротували посеред сеансу, потрапляють до запущеного сервера без перезапуску.

Файл env накладається на середовище процесу, а не замінює його: визначення облікових даних завжди читає поточне середовище процесу на момент запиту, тому змінні, наявні вже під час запуску (з оболонки або з блоку `env` клієнта), працюють і далі з прапорцем `--env.file` або без нього.  Під час повторного завантаження сервер записує лише ключі, які є у файлі й мають непорожні значення, і ніколи не скасовує значення жодної змінної, тому невдале або часткове повторне завантаження зберігає облікові дані, які працювали раніше.

Значення секретів ніколи не повертаються, не записуються в журнал і не потрапляють до журналу аудиту - інструмент повідомляє лише імена змінних і їхній стан.  Якщо прапорець `--env.file` не налаштовано, інструмент зводиться до простої перевірки стану.  Коли запит завершується помилкою під час визначення облікових даних, помилка MCP містить підказку, яка вказує агентові викликати інструмент `reload_credentials` і повторити спробу, тож агентні клієнти відновлюються самостійно.

:::note

Доступно у випусках StackQL після `v0.10.542`.

:::

## Вхідні дані {#inputs}

| Аргумент | Обов'язковий | Опис |
|--|--|--|
|`provider`|Ні|Обмежує звіт про стан одним провайдером.  Якщо аргумент не вказано, звіт охоплює кожен провайдер.|

* * *

## Вихідні дані {#output}

| Засіб відображення | Форма |
|--|--|
| Таблиця | Результат завантаження файлу env, а також один рядок на кожен провайдер зі станом визначення облікових даних |

<br/>

Структуроване корисне навантаження містить:

| Поле | Опис |
|--|--|
|`env_file`|Налаштований шлях `--env.file` (порожній, якщо шлях не налаштовано).|
|`env_file_sourced`|`true`, якщо файл знайдено й завантажено під час цього виклику.|
|`sourced_vars`|Імена змінних середовища, встановлених із файлу - лише імена, ніколи не значення.|
|`providers`|Один рядок на кожен провайдер (див. нижче).|

<br/>

Кожен рядок `providers` містить:

| Стовпець | Опис |
|--|--|
|`provider`|Ім'я провайдера.|
|`auth_type`|Тип автентифікації, налаштований для провайдера.|
|`sourced_from`|Джерело, з якого визначено облікові дані, наприклад `env:OKTA_SECRET_KEY`, `file:/path/key.json`, `inline` або `none`.|
|`status`|`ok`, `unresolved` або `not_checked`.|
|`detail`|Текст помилки для стану `unresolved`.|

<br/>

Типи автентифікації, які автентифікують поза шляхом байтів облікових даних (інтерактивний gcloud, Azure CLI, oauth2 client credentials, ланцюжки прийняття ролей, підписування OCI, null), повідомляють стан `not_checked`.

* * *

## Контроль {#gating}

Дозволено в усіх режимах сервера, зокрема в режимі `read_only` - інструмент не змінює нічого, крім власного середовища процесу сервера.

Не підтримується в режимі бекенду `reverse_proxy`: запити виконуються у віддаленому процесі сервера stackql, тому інструмент повертає помилку, яка вказує користувачеві повторно завантажити облікові дані на базовому сервері.

## Приклад {#example}

Спробуйте цей промпт у будь-якому клієнті MCP, у якому зареєстровано сервер MCP StackQL (запущений із прапорцем `--env.file`):

```
My okta query failed with a credential error - I've just written the key
to the credentials file.  Reload credentials and retry the query.
```
